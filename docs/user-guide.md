## 核心特性

- **国内 / 国际双站反代**：两个站点走同一套协议，凭据通过 `edition` 字段区分，刷新与对话自动路由到各自上游。
- **模型完全透传**：客户端传什么 `model` 就原样中继到上游，网关不维护转发白名单。`/v1/models` 仅用于客户端自动补全，不影响实际转发；`config.json` 的模型黑白名单是本地禁用规则，见[模型黑白名单](#模型黑白名单)。
- **模型列表双来源合并**：实时接口 + npm 静态目录，按 ID 去重、接口优先；失败用本地缓存，两边都失败且无缓存时该站点本轮不展示模型（不影响调用）。
- **模型倍率与价格探测**：促销生效时展示 `credits` × factor；默认不主动探测，正常模型请求仍会学习免费 / 收费状态。仅显式传入 `-allow-price-probes` 才开启后台实测，真实生成请求可能消耗积分。
- **多账号池 + 轮询负载均衡**：`-auth` 逗号分隔或 `-auth-dir` 目录，请求按 round-robin 分发；国内站与国际站账号可混挂。
- **模型级隔离**：`6004` 只冷却触发它的账号 + 模型，`14018` 只阻断该账号的当前收费模型，不再因为一个模型拖垮整个账号。
- **免费站点优先**：同一模型若「一个站点免费、另一个站点收费」，优先使用免费站点账号直至其受限；两个站点都收费（仅倍率不同）时不做倾斜，正常轮询。
- **免费/收费学习**：按「账号 + 模型」从响应 `usage.credit` 学习；`credit=0` 且样本足够（`total_tokens ≥ 100`）才判定免费，避免小样本误判。
- **国内站每日自动签到**：服务启动、凭据热加载时立即补签，之后每天 `UTC+8 09:00` 自动签到；国际站跳过。
- **凭据热加载（免重启）**：默认每 5 秒扫描凭据来源，新增 / 更新 / 删除凭据免重启生效。
- **授权失效自动禁用**：401/403 / `invalid token` / 登录过期时禁止调度、删除凭据文件并写入失效标记，重新 `login` 后自动恢复。
- **后台自动续期**：每 5 分钟检查 Token，距过期不足 15 分钟自动刷新并写回凭据文件；另可按 `-keepalive-hours` 在固定时刻主动刷新全部账号（默认每天 22:00），避免长期空闲账号静默失效。
- **流式分片规范化**：把上游每个分片携带的 `finish_reason:""` 归一化为 `null`，避免 Anthropic 翻译层误判 `stop_reason` 导致工具不执行。
- **工具调用序列自愈**：出站前按 `tool_call_id` 修复并行调用中夹入 message 的历史结构，合并 Responses API 拆散的并行调用，并删除无配对调用、孤儿或重复结果，避免国际站返回 `11148 tool_call_sequence_broken`。
- **OpenAI 兼容协议**：`/v1/chat/completions`（SSE 流式 + 非流式聚合）、`/v1/responses`（Responses API）、`/v1/models`、`/health`。
- **深度思考等级遵循 OpenAI 兼容规范**：对外接受 Chat Completions 的顶层 `reasoning_effort`、Responses 的 `reasoning.effort` / `reasoning.summary` / `text.verbosity`（含 `none` 关闭语义），归一化为上游认识的扁平字段。**仅当客户端显式传参时转发，绝不强制注入**，避免触发上游内容安全策略（详见[思考等级传参](#思考等级传参)）。
- **上游指纹对齐**：请求头逐项对齐官方客户端（详见[客户端指纹对齐](#客户端指纹对齐)），消除自造头与缺失头构成的可识别特征。
- **反审查净化**：自动改写 Claude Code 等框架被上游逐字拉黑的固定 Prompt 语句。
- **主动探测模型属性 (probe)**：余额耗尽的账号不会被正常调度，因而学不到「该账号该模型是否免费」。`probe` 子命令可主动探测并写入账本。
- **会话结构自动归一化**：自动保证首条消息为 `system`，修复部分非 harness 客户端（以 `assistant` 续写或以 `tool` 回传工具结果开头）触发的上游 `first message is not system prompt` (code 11128) 报错；同时兼容 OpenAI 新版 `developer` 角色。
- **单账号串行化**：同一账号请求自动排队，避免并发双发触发上游风控；不同账号之间可并行。
- **一键重置 (`reset`)**：清空除登录凭据外的全部本地数据（状态快照 / 模型缓存 / 日志 / 失效标记），并立即重新拉取模型目录与倍率。
- **纯 CLI 控制**：终端内嵌 ASCII 二维码，国内站微信 / 企业微信扫码登录；`status` / `refresh` / `serve` 子命令完成全部管理。
- **Anthropic 协议原生入口**：`/v1/messages`（SSE 流式 + 非流式聚合）与 `/v1/messages/count_tokens`，Claude Code 等 Anthropic 客户端免外部翻译层直连，鉴权兼容 `x-api-key` 头。

## 命令总览

```text
workbuddy-gateway [command] [options]

命令:
  serve     启动本地网关（默认命令，不带子命令时等同 serve）
  login     登录并获取 / 更新凭据
  status    查看账号池状态
  refresh   手动刷新所有账号访问令牌
  monitor   前台实时监控：账号表格 + 模型统计附表 + 最近日志
  probe     主动探测账号对指定模型的免费 / 收费属性（需 serve 运行中）
  reset     清空除登录凭据外的全部本地数据，并重新拉取模型与倍率
  version   查看版本信息
  help      查看帮助
```

全局选项（对所有命令可用）：

| 选项 | 默认 | 说明 |
|---|---|---|
| `-addr <ip>` | `127.0.0.1` | 网关监听地址 |
| `-port <port>` | `8317` | API 监听端口；显式传入时覆盖 `config.json` 的 `gateway.apiPort` |
| `-auth <path>` | 自动发现 | 凭据文件路径，支持逗号分隔多个 |
| `-auth-dir <dir>` | 空 | 凭据目录，自动加载目录内所有 `workbuddy*.json` |
| `-proxy <url>` | 空 | 上游请求代理，如 `http://127.0.0.1:7890`、`socks5://...` |
| `-verbose` | `false` | 输出详细调试日志 |
| `-intl` | `false` | 仅 `login` 生效：登录国际站 |
| `-reload-interval <sec>` | `5` | 凭据热加载扫描间隔，`0` 关闭 |
| `-models-refresh <min>` | `60` | 模型目录刷新间隔，`0` 关闭 |
| `-allow-price-probes` | `false` | 允许后台自动价格探测；会发起真实模型生成请求，可能消耗积分。默认关闭，不影响正常请求学习、目录刷新及显式 `probe` 命令 |
| `-webui` | `false` | 启用独立网页控制台（默认 `http://127.0.0.1:8316/ui/`）；管理 Key 与模型 API 鉴权由 `config.json` 配置 |

**价格探测默认关闭（含旧版本升级）**：只有显式指定 `-allow-price-probes` 或 `-allow-price-probes=true` 才开启后台价格探测。旧启动脚本中的 `-disable-price-probes` 仍可使用；两个参数同时传入且旧禁用参数为 `true` 时，禁用优先，与参数顺序无关。仅传入 `-disable-price-probes=false` 不会开启探测。此开关是启动参数，修改后需重启服务。

```bash
# 默认不主动生成价格探测请求；正常客户端请求仍自动学习计费状态
workbuddy-gateway serve -webui

# 明确允许主动探测；可能产生额外积分消耗
workbuddy-gateway serve -webui -allow-price-probes
```

### 配置网页控制台与模型 API 鉴权

工作目录 `config.json` 的 `gateway` 段控制监听端口、网页控制台管理 Key 和模型 API 鉴权，全部为明文配置（`config.json` 已被 Git 忽略，请自行限制文件权限）：

```json
{
  "gateway": {
    "apiPort": 8317,
    "webPort": 8316,
    "adminKey": "",
    "apiKeyEnabled": false,
    "apiKey": ""
  }
}
```

| 配置 | 默认 | 说明 |
|---|---|---|
| `apiPort` | `8317` | 模型 API 监听端口，省略或 `0` 使用默认值；也可用 `-port` 临时覆盖 |
| `webPort` | `8316` | 网页控制台监听端口，省略或 `0` 使用默认值；仅在显式 `-webui` 时监听 |
| `adminKey` | `""` | 网页控制台管理 Key，有两种设置方式：**① 页面一键生成**——为空时在服务器本机（或 SSH 本地端口转发）打开网页，生成 32 字符随机 Key 写入本文件，并在弹窗中**仅展示一次**；**② 手动编辑本文件**——直接把本字段改成任意随机字符串（建议 32 位），保存后约 1 秒热生效。设置完成后可从其他设备用该 Key 登录 |
| `apiKeyEnabled` | `false` | 模型 API 是否校验 Key。关闭时不带 Key 或任意 Key 均可调用模型；开启时必须匹配 `apiKey` |
| `apiKey` | `""` | 模型 API Key。开启校验时必须非空；关闭时保留原值，重新开启即可继续使用 |

网页控制台也可在「访问设置」页切换 `apiKeyEnabled` 并设置 `apiKey`，保存后立即生效并写回本文件；端口修改需要重启。管理 Key 与模型 API Key **相互独立**：关闭模型 API 鉴权不会关闭管理鉴权，模型 API Key 也不能登录网页控制台。为避免他人抢先生成，**页面一键生成**管理 Key 只允许本机访问；**手动编辑 `config.json` 设置 `gateway.adminKey`** 不受此限制，效果与一键生成完全相同。

> **升级顺序（重要）**：新版本能读取不含 `gateway` 段的旧配置，但**旧版本二进制遇到含 `gateway` 段的新配置会启动失败**（`json: unknown field "gateway"`）。请**先替换二进制、再添加 `gateway` 配置**。

### JSON 调试日志

工作目录中的 `config.json` 控制结构化调试日志，默认关闭。修改后约 1 秒热生效，无需重启：

```json
{
  "debug": {
    "enabled": true,
    "fullRequests": false
  }
}
```

`config.example.json` 和首次部署的默认配置显式写出 `enabled: false`、`fullRequests: false`。缺少 `debug` 段、`debug` 为 `null`/空对象/空字符串，或任一值缺失/为空时均按 `false` 处理；`0/1`、`"true"/"false"` 也会容错解析，未知子字段忽略。

开启后，网关把单行 JSON 写入 `logs/debug-YYYY-MM-DD.jsonl`；普通运行日志仍写入原来的 `logs/gateway-YYYY-MM-DD.log`，两者互不替代。可复制 `config.example.json` 作为起点。

### 日志保留与清理

```json
{
  "logs": {
    "retentionDays": 7
  }
}
```

- `retentionDays` 范围为 `0～36500`：`0` 或省略表示保留全部，兼容旧配置；`7` 表示按服务器本地日期保留今天及此前 6 天。**设为正数后会自动删除过期日志，删除不可撤销。**
- 配置热加载后应用新规则；启动/规则变化时扫描，此后每小时自动扫描。网页「日志」页可以保存保留天数，也可以立即按已保存规则清理。
- 只删除 `logs/` 内日期合法的 `gateway-*.log`、`debug-*.jsonl`、`deployment-*.jsonl`、`frontend-*.log`；不跟随符号链接，不删除目录、凭据、配置、报告或其他文件，不删除正在写入的日志。
- 普通日志和调试日志在跨午夜后的下一次写入切换到新日期文件。尚未切换的旧日志保持保护，关闭后在后续扫描清理。
- 请先替换新二进制，再添加 `logs` 段；旧二进制可能因未知配置字段拒绝启动。

### 配置系统提示词

工作目录 `config.json` 的 `systemPrompt` 段有两个独立选项（修改后约 1 秒热生效）：

```json
{
  "systemPrompt": {
    "fallback": "",
    "force": ""
  }
}
```

| 配置 | 空值的默认行为 | 非空时的行为 |
|---|---|---|
| `fallback` | 继续使用 `You are a helpful assistant.` | **仅在客户端没有任何 system 时**，替换网关注入的保底提示词；已有 system 不变 |
| `force` | 不启用；请求提示词完全按原规则处理 | **实验功能**：在 Chat、Responses、Anthropic Messages 三个入口的首条 system 内容**末尾追加**配置文本（后置），使其成为位置最靠后、紧贴用户消息的指令；原 system 内容仍完整保留 |

例如 `{"systemPrompt":{"fallback":"你是一个助手。","force":"请用中文回答。"}}`：客户端没有 system 时，发往上游的是 `你是一个助手。\n\n请用中文回答。`；客户端自带 system 时，发往上游的是 `<客户端原 system>\n\n请用中文回答。`。配置值仅支持 JSON 字符串；空串或全空白视为未配置。不会写出或替换客户端的 user、assistant、tool 消息，也不改变账号选择。普通日志和普通 JSON 调试模式只记录规则分支、位置与字符数；显式开启 `debug.fullRequests` 后，完整请求事件会包含处理前后的提示词正文。

> **实验功能风险自负：** `force` 后置于 system 末尾（紧贴用户消息），因此比客户端自带指令更"新近"，冲突时通常更有影响力——这正是人设类、风格类指令希望达到的效果，但也可能与客户端的 system 指令冲突、改变模型行为、增加 token 消耗，或触发上游内容/参数校验。需要回退时将 `force` 改回 `""` 并保存；建议先在测试会话验证，切勿在配置中写入密码、密钥或个人隐私。`config.json` 已被 Git 忽略，不要将真实配置提交到仓库。

`/v1/messages/count_tokens` 仅对客户端提供的内容做本地近似估算，不调用上游，也不计入网关随后注入的 `fallback` / `force` 文本；最终消耗以模型返回的 usage 为准。

### 套餐识别与官网一致性

从 v1.13.9 起，账号套餐不再仅凭 `ProTrialStatus=1` 判定为“Pro试用”。每轮额度刷新会额外调用官网的只读通用资源接口，根据有效状态、权益起止时间及当前订阅信息确认套餐：

- 查询不限定 `PackageCodes`，支持分页；官网新增套餐编码不会被固定名单漏掉。
- 名称按站点区分：国内站四档规范显示为 **体验版 / 标准版 / 高级版 / 旗舰版**；国际站保留 **免费 / pro / Pro试用**。国内标准版不会误标为国际站 pro。
- 新套餐优先显示接口返回的 `PackageName`，历史套餐也不会强行归入四档。新编码没有名称时显示“未识别订阅”，不猜成 Free 或 Pro。
- 赠送积分包、加量包不当成订阅；额度用尽但权益未到期的套餐仍保留套餐身份。
- 已过期、退款、尚未生效的权益不当成当前套餐。试用标记仍为 `1`，但已无有效试用且只有 Free 权益时，显示“免费”。
- 查询失败或遇到无法解释的字段/子产品时，已有核验结果标 `*`（待刷新），无核验结果显示“待确认”。额度查询成功时仍正常更新额度，不因套餐识别失败丢弃额度。
- 快照增加 `planCheckedAt`、`planStale` 字段。旧版本未核验的套餐标签不会作为可信结果沿用；新版本启动后会重新校验。

兼容边界：同一产品和资源字段结构下新增套餐通常可直接展示官方名称；若官网改变产品编码、接口、状态枚举或权益规则，仍可能需要更新程序。这不是对未来任意接口变更的保证。此过程只查询会员/额度信息，不领取试用、不购买/续费，也不请求模型。

### 企业成员账号

凭据中的 `account.enterpriseId` 非空时，额度查询改用只读接口
`POST /v2/billing/meter/get-enterprise-user-usage`，不再把个人资源包为空误判成企业额度耗尽。

- `limitNum` 是分配给这个成员的额度，`credit` 是本周期已用；剩余为 `max(0, limitNum - credit)`，保留小数。兼容 `limit_num`、`used_num`、`usedNum`。
- `limitNum = -1` 表示不限量，总额度与剩余额度显示「不限」；它不是余额为零，也不是查询未知。
- 显示「企业版」只表示账号类型，不推断个人套餐等级、企业管理员身份或企业池总额度。成员额度与企业池余额是两回事。
- 企业号跳过个人签到，令牌续期与额度扫描继续执行。企业额度恢复后自动清除模型额度阻断，但保留账号/模型限流冷却；真实模型请求若返回 `14018`，仍会阻断，不能用「不限量」绕过上游拒绝。
- 企业接口超时、失败、缺少额度/已用字段、字段冲突或数值无效时，保留上次额度并标记待刷新，不把失败当成 0，也不自动切回个人接口。
- 以上分支已由本地模拟上游、三个 API 入口集成测试及网页测试覆盖；没有企业凭据的环境不能据此声称已完成真实企业账号联调。

### 登录凭据自动续期（保活）

登录凭据分两种令牌：**访问令牌**用于请求模型和查询额度；**刷新令牌**用于换取新的访问令牌。刷新令牌本身也有有效期，一旦它到期或被上游判定失效，就必须重新 `login`，程序无法绕过。

从 v1.13.11 起，网关同时使用两条触发路径续期：

| 触发方式 | 时机 | 说明 |
|---|---|---|
| 临近过期续期 | 后台每 5 分钟检查，访问令牌剩余不足 15 分钟时刷新 | 保证请求不会用到过期令牌 |
| **主动定时续期** | `-keepalive-hours` 指定的本地时刻（默认 `22`，即每天 22:00） | 不等访问令牌临近过期就刷新全部账号，避免长期空闲账号静默失效 |

```bash
# 默认每天 22:00 主动续期
workbuddy-gateway serve

# 每天 10:00 和 22:00 各一次
workbuddy-gateway serve -keepalive-hours 10,22

# 关闭主动续期，只保留临近过期时的按需刷新
workbuddy-gateway serve -keepalive-hours ""
```

实现要点：

- **只调刷新接口**，不请求模型、不消耗额度、不产生对话记录。
- **串行 + 节流**：账号之间间隔 1 秒逐个刷新，避免批量并发刷新形成机器特征。
- **启动补跑**：距上次成功续期超过 20 小时的账号，在服务启动 90 秒后补做一轮，避免重启错过时刻。
- **失败不轻易删号**：单次失败只累计计数并保留原凭据；连续失败 3 次才判定登录态失效并停止调度。上游明确返回会话失效（如 `12153` / `invalid_grant`）时首次即告警，但仍保留凭据等待阈值。
- **记录续期元数据**：刷新成功后把 `refreshExpiresAt`、`lastRefreshTime` 写回凭据文件，`status` 与 `monitor` 会显示刷新令牌到期时间，并在剩余不足 7 天或已过期时给出重新登录提醒。
- **不掩盖问题**：刷新成功但访问令牌期限没有顺延时会单独告警，提示该账号可能已接近上游的登录态上限。

> **注意刷新令牌是独占的。** 每次续期上游通常会下发新的刷新令牌并让旧的失效。如果同一个账号的凭据还被其他工具（脚本、其他网关、桌面客户端）同时使用，双方会互相把对方的刷新令牌作废。请确保一个账号只由一处负责续期。`-keepalive-hours` 留空即可关闭本功能。

#### 凭据覆盖与删除前的校验

凭据文件是登录态的唯一副本，删掉就只能重新登录。因此「覆盖」和「删除」这两个不可逆动作之前都会先做只读校验。

**续期成功、准备覆盖旧凭据之前：**

| 检查 | 目的 | 不通过时 |
|---|---|---|
| 新旧凭据账号标识一致（访问令牌 `sub`） | 防止上游串号或响应错配，把凭据写到别的账号上 | 拒绝覆盖，保留旧凭据并告警 |
| 新旧凭据站点一致（`iss` realm） | 防止国内站/国际站凭据互相覆盖 | 同上 |
| 新访问令牌能取到账号数据 | 防止「接口返回 200 但实际不可用」的凭据覆盖掉还能用的旧凭据 | 同上 |

校验接口自身不可用时按通过处理，不会因为校验抖动而拒绝有效的新凭据。校验失败**不计入**「判定失效」的计数，因此不会把还能用的账号停掉。

**判定失效、准备删除凭据之前：**

1. 先停止调度并写入失效标记；
2. 再用只读接口确认该凭据确实取不到账号数据，**才**删除文件；
3. 凭据仍能取到数据 → 保留文件；
4. 无法判定（网络故障、上游 5xx）→ 保守保留文件。

凭据文件被保留时，失效标记在重启后依然生效，账号不会被重新调度。如果你重新 `login` 或手动续期了该凭据，凭据文件会比标记更新，网关会自动清除过期标记并恢复该账号。

### 模型黑白名单

`config.json` 的 `models` 段可按模型名启用黑白名单（大小写与首尾空白不敏感）：

```json
{
  "models": {
    "blocklist": ["deepseek-v4-pro"]
  }
}
```

| 字段 | 说明 |
|---|---|
| `blocklist` | 黑名单，命中即禁用 |
| `allowlist` | 白名单，**非空时**只放行列表内模型，其余一律禁用 |

规则：

- 模型黑名单与白名单**选择一种**。非空 `allowlist` 和非空 `blocklist` 同时存在会校验失败，避免配置歧义；旧示例同时包含两个空数组、或其中一个为空时仍可读取。
- 两个列表都为空或省略时不做任何限制（默认行为不变）。
- 被禁用的模型会从 `/v1/models`、`/health` 的 `model_count` 和 `monitor` 的模型统计附表中**直接隐藏**。
- 请求被禁用模型时返回 `403` 与中文提示，**不会消耗任何上游账号额度**：

```json
{
  "error": {
    "message": "模型 deepseek-v4-pro 已被网关禁用（命中黑名单），请联系管理员调整 config.json",
    "type": "model_disabled",
    "code": 403
  }
}
```

`serve` 启动横幅会打印当前名单状态，例如 `模型黑白名单: 已启用 (黑名单 1 个 / 白名单 0 个...)`。

### 按模型限制账号文件

`models.accounts` 是凭据 JSON 文件黑白名单：保留键 **`all`** 控制所有模型的全局账号调度，其余键控制对应模型。未配置 `all` 或全局列表为空时与旧版本相同。全局规则和模型专属规则**都通过**才允许调度，模型专属白名单不能绕过全局停用。与上面的 `models.allowlist` / `models.blocklist`（控制模型是否可调用）互不替代：

```json
{
  "models": {
    "blocklist": [],
    "accounts": {
      "all": {
        "allowlist": [],
        "blocklist": ["paused-account.json"]
      },
      "deepseek-v4.1-flash": {
        "allowlist": ["intl-a.json", "intl-b.json"],
        "blocklist": ["intl-b.json"]
      },
      "hy3": {
        "blocklist": ["old-account.json"]
      }
    }
  }
}
```

- 同一模型内黑名单优先；账号白名单为空表示不限制，黑名单为空表示不排除。上述示例中 `deepseek-v4.1-flash` 最终只允许 `intl-a.json`，`hy3` 仅排除 `old-account.json`。
- `all.blocklist` 中的账号不再参与任何模型的请求调度、失败换号和模型生成探测。账号仍显示在管理台，凭据、额度账本和历史统计保留；后台凭据保活/额度查询不属于模型生成，保持原有行为。
- 全局账号白名单非空时，账号池开关反映白名单规则。首次网页账号操作会删除 `all.allowlist`（包括空数组或 `null`），将**当前账号池**的全局启停状态转换为 `all.blocklist`，再应用本次操作；其他当前账号状态和模型专属规则保留，之后新增账号默认开启（黑名单语义）。
- 只接受凭据**文件名**（如 `intl-a.json`），不接受路径或通配符；同名凭据位于多个目录时会拒绝匹配，避免误用。模型名忽略大小写，文件名必须与实际凭据文件一致。
- 请求调度与失败换号都不会绕过账号名单；后台价格探测与本机 `/admin/probe` 也会跳过不允许的账号。若没有匹配的账号，请求返回 `403 model_account_disabled` 中文提示，且不会调用上游。
- 实时运行日志 `logs/gateway-YYYY-MM-DD.log` 在有账号被排除时记录汇总一行（模型、候选账号数、排除明细）；开启调试时 `logs/debug-YYYY-MM-DD.jsonl` 记录每个账号的 `model_account_policy_checked`。`monitor` 模型统计表的“可用账号”列已按名单过滤，只统计符合规则的账号。
- 修改 `config.json` 约 1 秒热生效；示例中的文件名均为占位值。没有配置 `models.accounts` 时原行为不变。

### config.json 热生效与旧版本升级

`serve` 独立每 1 秒按文件内容检测配置变化，不受 `-reload-interval 0`（只关闭凭据扫描）影响。网页开关先写入配置文件、再立即应用；外部编辑器修改则在下一次扫描应用。

| 配置 | 生效方式 |
|---|---|
| 模型名单、`models.accounts`（含 `all`） | 热生效，控制后续调度 |
| `gateway.adminKey` / `apiKeyEnabled` / `apiKey` | 热生效；管理 Key 改变后需使用新 Key 登录 |
| `systemPrompt` / `debug.enabled` / `debug.fullRequests` | 热生效 |
| `upstream` 超时、网络重试次数 | 后续上游请求使用新值；已有流式响应保持原空闲超时 |
| `gateway.apiPort` / `webPort` | 写入配置但**重启后**变更监听；页面仍显示实际监听端口 |

- 配置先整体解析、校验，再应用。运行时遇到半写 JSON、空文件、文件短暂缺失、错误类型或非法账号路径时，**保留上一份有效配置**，错误原因写入 `logs/gateway-YYYY-MM-DD.log`。修正并保存后自动重试；不会把配置读取失败误当作“全部开启”。
- 要恢复默认规则，请保存有效的 `{}` 或将对应列表设为 `[]`，而不是删除运行中的配置文件。
- 上一版本省略 `all`、`accounts`、`models` 或 `gateway` 的配置仍可读取；`accounts: {}`、`accounts: null`、`all: {}` 和空名单均表示无全局限制。默认示例包含空的 `models.accounts.all.allowlist/blocklist`。
- 如旧配置同时填写了**两种非空模型名单**，请在升级前选择并保留一种；新版本不再接受相互冲突的模型黑白名单。运行中错误配置会保留上次生效状态，启动时则给出明确错误。
- 旧配置中只有白名单生效时，管理页开关反映白名单；首次网页模型操作会删除 `models.allowlist`，将**当前已知模型**的启停状态转换为 `models.blocklist`。其他已知模型状态不变，之后新增的模型默认开启（黑名单语义）。模型账号规则保持独立。
- 新版本中的 `all` 是保留键；不要把它当作真实模型 ID。**先升级二进制，再添加 `all`**；旧二进制不识别全局语义，会把它当作名为 `all` 的模型专属规则。

每条 JSON 调试日志都包含时间、级别、稳定事件名、`trace_id`、`request_id`、服务/实例/版本、路由、方法、模型、账号、流式标记和累计耗时，并记录客户端地址、代理头、协议、TLS、Content-Type、Content-Length、deadline 等请求元数据。客户端传入的 `X-Trace-ID` 会优先作为日志里的 `trace_id`；出站上游的链路头仍只由会话作用域对齐写入，调试开关不会覆盖它们。

普通调试模式（`debug.fullRequests` 缺省或为 `false`）不记录完整请求体，也不记录明文 `Authorization`、Cookie、API Key、Access Token、Refresh Token。只记录以下安全摘要：

- `declared_body_bytes`、`actual_body_bytes`、`body_read_ms`
- `body_sha256_prefix`（SHA-256 前 12 位）
- `json_valid`、`json_decode_ms`
- `body_limit_bytes`、`body_limit_exceeded`（当前未设置请求体限制，因此分别为 `0`、`false`）
- `read_error_type`、脱敏截断后的 `read_error`

#### 完整请求对比日志（显式开启）

排查不同客户端或协议转译差异时，合并以下设置到现有配置；不要用此片段覆盖整份配置：

```json
{
  "debug": {
    "enabled": true,
    "fullRequests": true
  }
}
```

两个开关都开启才生效，约 1 秒热加载，无须重启。关闭 `fullRequests` 即恢复普通调试日志；关闭 `enabled` 则关闭全部 JSON 调试日志。正式功能没有临时采集的 30 分钟或 200 次限制。

记录仍写入 `logs/debug-YYYY-MM-DD.jsonl`，按 `trace_id` 串联：

| 事件 | 内容 |
|---|---|
| `full_request_inbound_headers` | 模型 API 入站方法、URL、请求头；此时未读取正文 |
| `full_request_inbound` | 鉴权通过后读取的完整客户端 JSON 请求体，位于 `body` |
| `full_request_upstream` | 协议转换、系统提示词规则及历史修复后的完整上游 JSON；包含实际构造的出站请求头 |
| `full_request_upstream_result` | 每次发送的 HTTP 状态、响应头、请求头/请求体是否写出、网络错误类型 |
| `full_request_upstream_error` | 已读取的上游错误 JSON，例如 `11128`；不预读成功响应流 |

同一请求的换号通过 `acc` 区分，网络重试通过 `attempt` 区分，具体发送通过 `upstream_request_id` 关联。`user_agent` 顶层字段始终是客户端 UA，实际出站 UA 看 `full_request_upstream.request.headers`，不要混淆两者。

完整 JSON **不截断**，包括所有消息、工具定义和图片数据；JSON 空白/转义可能重新序列化，不是逐字节原始抓包。凭据字段、Cookie、已知密钥及 URL 中的凭据参数会脱敏；请求头敏感字段另有进程内随机密钥生成的 HMAC 摘要，用于同一进程内判断是否相同，重启后不能跨进程比较。不合法或读取不完整的 JSON 标记为省略，避免损坏 JSON 的凭据泄露，不伪装为完整采集。

鉴权/CORS/方法拦截不会为了日志而额外读取正文；相关拒绝原因仍由原有中间件事件记录。管理配置、账号登录及凭据接口不属于完整正文采集范围。

**隐私与磁盘提示：** 完整请求包含真实对话、源代码、工具输入和图片，即使凭据脱敏也仍属敏感日志。无法保证识别正文内所有任意格式的秘密。文件按 `0600` 创建（Windows 还应检查目录 ACL），不要上传或公开分享原始日志。多兆请求会迅速增加磁盘占用和日志写入耗时，建议仅排障期间开启；沿用 `logs.retentionDays` 的既有日志清理策略。网页日志查看器有读取大小限制，完整比对应读取服务器文件。

## serve

启动本地网关，默认命令。

```bash
# 默认监听 127.0.0.1:8317，自动加载当前目录下所有 workbuddy*.json
workbuddy-gateway serve

# 自定义端口与监听地址
workbuddy-gateway serve -port 9000 -addr 0.0.0.0

# 显式指定多个凭据文件（逗号分隔，轮询）
workbuddy-gateway serve -auth workbuddy.json,workbuddy2.json

# 目录模式：加载目录内所有 workbuddy*.json
workbuddy-gateway serve -auth-dir ./auths

# 上游走代理 + 详细日志（客户端鉴权在 config.json 的 gateway 段配置）
workbuddy-gateway serve -proxy http://127.0.0.1:7890 -verbose

# 关闭凭据热加载
workbuddy-gateway serve -reload-interval 0

# 关闭模型目录自动刷新
workbuddy-gateway serve -models-refresh 0
```

启动后提供的端点：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/chat/completions`、`/chat/completions` | Chat Completions，支持 SSE 流式与非流式 |
| POST | `/v1/responses`、`/responses` | OpenAI Responses API |
| POST | `/v1/messages` | Anthropic Messages API（Claude Code 直连，内部转 Chat 走同一条上游管线） |
| POST | `/v1/messages/count_tokens` | Anthropic 令牌计数（本地估算，CJK 1 token/字、ASCII 4 字符/token） |
| GET | `/v1/models`、`/models` | 模型列表，响应头 `X-Model-Source` 标注来源 |
| GET | `/health`、`/ping` | 健康检查，返回 `version`、`model_count`、`model_source` |
| POST | `/admin/probe` | 供 `probe` 命令调用，**仅接受回环来源** |
| GET | `/ui/` | 网页控制台静态页面（独立端口，仅 `-webui` 启用时存在） |
| GET | `/admin/api/*` | 网页控制台数据接口（独立端口，仅 `-webui` 启用时存在，需管理 Key） |
| GET | `/` | 简单文本说明 |

从 v1.13.15 起，Responses `function_call_output.output` 支持文本和图片内容块数组：
文本原样保留在 `tool` 结果中，`input_image` 图片提升为全部配对工具结果之后的
`user` 多模态消息，图片 URL 和数据不变。图片不再被序列化成 Base64 文本混入
上下文，避免截图会话异常消耗大量 token，最终触发 `11133 model_param_invalid`。
并行工具调用的结果仍连续排列，不会因插入图片而破坏配对。普通字符串和 JSON
工具结果保持原行为；网关不截断操作手册或会话历史。`11133` 本身是上游通用参数
错误码，不仅限于图片或上下文长度问题；排障仍需结合模型、TraceID 与日志。

从 v1.13.17 起，网关在客户端未声明输出预算（`max_tokens` 与 `max_completion_tokens`
都不带有效值）时，按模型目录声明的输出上限补一个 `max_tokens`。上游按「输入 token +
输出预算」判断是否超出模型窗口，而请求不带该字段时上游会为输出默认预留 384000：
标称 1048576 窗口的 `deepseek-v4.1-flash` 实际只剩约 664576 可用输入，长会话会在远未
到窗口上限时被 `11133 model_param_invalid` 拒绝，表现为「聊着聊着就 400」。实测
678912 输入不带预算返回 `400/11133`，带 `max_tokens=128000` 返回 `200`。客户端显式
传入的值一律不覆盖；目录未收录的模型保持原行为，网关不做猜测。注意可用输入与输出上限
共用同一窗口（可用输入 = 窗口 − 声明的输出预算），需要更长输入时应让客户端声明更小的
输出预算，而不是更大。

后台任务（`serve` 启动后按启用条件运行）：

| 任务 | 周期 | 说明 |
|---|---|---|
| Token 续期检查 | 5 分钟 | 距过期不足 15 分钟自动刷新 |
| 额度扫描 | 5 分钟 | 每凭据 10 秒超时，超时保留旧值；`剩余=0` 标记付费耗尽 |
| 模型目录刷新 | 60 分钟 | 实时接口 + npm 目录，合并去重后写缓存 |
| 模型价格探测 | 默认关闭；开启后首轮约 20 秒，随后 2 或 30 分钟；同站点同模型至少间隔 12 小时 | 仅 `-allow-price-probes` 开启；无探测记录时单轮最多 30 个，之后最多 5 个；真实生成请求可能消耗积分 |
| 每日签到 | 每天 `UTC+8 09:00` | 仅国内站 |
| 状态快照 | 3 秒 | 写 `workbuddy-status.json` 供 `monitor` 读取 |
| 凭据热加载 | 5 秒 | 扫描凭据新增 / 更新 / 删除 |

**上游超时策略**

网关不再对上游请求设置「整条流的总超时」，避免长时间但持续有输出的流被中途掐断（会丢失 usage、返回残缺内容，并被上游代理判为故障触发 503）：

| 阶段 | 策略 |
|---|---|
| 连接与响应头 | `ResponseHeaderTimeout` 默认 300 秒。上游对 3MB+ 大请求排队+预处理可能接近 1 分钟（实测 2.3MB 请求曾需 50.8s 才回响应头），因此默认放宽到 5 分钟兜底 |
| 流式响应体 | 空闲读超时默认 120 秒：持续有数据就永不超时，只有 120 秒无任何新数据才判定卡死并中断 |
| 控制类短请求 | 令牌刷新 / 额度查询 / 模型目录等 60 秒超时 |
| 服务端写响应 | 不设总时长上限（原 300 秒），长流不会被服务端截断 |

两个上游超时可在工作目录 `config.json` 的 `upstream` 段覆盖（单位秒，省略或非正数则用默认值）：

```json
{
  "upstream": {
    "headerTimeoutSeconds": 300,
    "idleTimeoutSeconds": 120,
    "transientRetries": 2
  }
}
```

**瞬时网络错误重试**

网关与上游 CDN 边缘节点之间的单条 TCP 连接可能被对端重置（`connection reset by peer`）、被关闭（`use of closed network connection`），或命中已被回收的 keep-alive 连接。这类错误属于瞬时故障，与请求体大小无关（实测 >5MB 请求 95% 成功，而 0.5MB 请求也会偶发失败）。

只有**请求头尚未写出**时，才能确认上游不可能处理本次 POST，网关才对瞬时连接错误重试。`Do` 返回 EOF、RST 或超时但请求头已写出时，上游可能已经收到并处理请求；即使尚未收到响应头，也不会自动重放，以免重复生成。

| 项 | 默认 | 说明 |
|---|---|---|
| 重试次数 | 2 | `upstream.transientRetries` 可覆盖；显式设为 `0` 可禁用 |
| 重试间隔 | 300ms | 给上游边缘节点留出恢复时间 |
| 重试范围 | 请求头未写出时的瞬时错误 | 包括建连阶段 EOF、RST、`broken pipe`、`connection refused` 等 |
| 不重试 | — | 请求头已写出的 EOF/RST/超时（执行结果不确定）、客户端取消、上游 HTTP 错误响应 |
| 连接处理 | 新连接 | 重试时设置 `Connection: close` 并 `CloseIdleConnections()`，避免复用坏连接 |

重试会在日志中留下明确记录：

```text
[网络重试] traceId=... requestId=389 账号=example.json 第 1/2 次重试，上一尝试请求头未写出，已重建连接
```

启动横幅会打印生效值，便于确认。流被中断时不会伪造 `[DONE]`（chat）或 `response.completed`（Responses），而是下发明确的 `upstream_stream_interrupted` / `response.failed` 错误事件，避免下游把残缺输出当成完整结果。

## webui（网页控制台）

默认关闭。显式 `-webui` 后在 `gateway.webPort`（默认 `8316`）提供独立网页控制台，用于管理账号池开关、模型列表开关，查看和清理日志、预览及编辑 `config.json`、查看定时任务记录，并在「访问设置」页切换模型 API Key 校验或编辑端口。网页不展示凭据页面。它与模型 API 端口分离，未启用时管理端口不监听。

```bash
# 只有显式 -webui 才开启网页控制台；模型 API 仍监听 8317
workbuddy-gateway serve -webui

# 方式一：本机或 SSH 本地端口转发打开页面，一键生成管理 Key
ssh -L 8316:127.0.0.1:8316 root@服务器
# 浏览器打开
# http://127.0.0.1:8316/ui/

# 方式二：不打开页面，直接在服务器上手动设置管理 Key（建议 32 位随机字符串）
python3 - <<'PY'
import json, secrets, pathlib
p = pathlib.Path("/opt/workbuddy-gateway/config.json")
cfg = json.loads(p.read_text())
cfg.setdefault("gateway", {})["adminKey"] = secrets.token_hex(16)  # 32 字符
p.write_text(json.dumps(cfg, ensure_ascii=False, indent=2) + "\n")
print("已写入 gateway.adminKey，运行中的新版本约 1 秒热生效")
PY
systemctl restart workbuddy-gateway
```

| 项 | 说明 |
|---|---|
| 入口 | `GET /ui/`（独立管理端口，静态外壳不含任何数据） |
| 数据接口 | `GET /admin/api/status`、`/admin/api/models`、`/admin/api/logs`、`/admin/api/config`、`/admin/api/tasks`，**一律需要 `Authorization: Bearer <adminKey>`** |
| 写入接口 | `POST /admin/api/setup`（仅本机首次生成管理 Key）、`POST /admin/api/settings`（模型 API 鉴权与端口）、`POST /admin/api/account-toggle` / `model-toggle`（账号/模型开关）、`POST /admin/api/credential-edit`（凭据 JSON）、`POST /admin/api/log-settings` / `log-cleanup`（保留设置与过期清理） |
| 页面 | 总览（用量趋势、账号池健康度与日志告警）、账号池（全局调度开关）、模型列表（启停开关，含停用模型；请求数、平均首 Token、平均总耗时、总 Token 按 `stats.json` 聚合近 5 小时）、日志（保留天数与清理）、配置（Key 脱敏预览；确认警告后可编辑完整配置，systemPrompt 正文直接展示）、定时任务（只读日志视图）、访问设置（鉴权与端口编辑）。网页不再提供凭据列表或编辑器 |
| 数据来源 | 复用 `serve` 的状态快照、完整模型目录、`logs/` 日志与本地配置/凭据文件；开关受控写入配置并应用原有调度过滤 |
| 定时任务 | 周期、启用状态、最近执行、完成时间、执行结果、下次预计执行与日志说明；仅展示、不触发任务或修改调度 |

#### 网页新增账号与删除凭据

账号池页顶部有「添加账号」，点开后：

1. 选择**国内站**或**国际站**；
2. 填**凭据名**，默认是运行目录下第一个没被占用的 `workbuddyN.json`。只能改文件名，落地目录固定为程序运行目录（设置了 `-auth-dir` 时用该目录），页面不展示绝对路径；
3. 点「获取登录接口」，表单内直接显示**登录链接与二维码**；
4. 手机扫码授权后，网关自动写入凭据、自动并入账号池并触发额度扫描，**不需要重启服务**。

这条流程与命令行 `workbuddy-gateway login -auth <文件>`（国际站加 `-intl`）**复用同一套登录实现**，行为一致，不会出现两套逻辑漂移。登录会话有时限（国内站 5 分钟、国际站 15 分钟），页面显示剩余时间；超时后提示登录链接已失效并停止轮询，已结束会话会短暂保留以便网页读取终态，点「关闭」也会停止轮询，两种情况都不写入任何文件。

账号表每行末列有「删除」按钮：确认后删除该账号的凭据文件或残留失效标记，并立即从账号池和状态快照移除。**只删除凭据相关文件**，历史统计与日志保留。以下情况一律拒绝删除：同名凭据存在多个、文件名不符合 `workbuddy*.json`、目标不是普通文件（目录或符号链接）、账号不存在。

#### 只读定时任务与访问设置

- 「定时任务」通过只读 `GET /admin/api/tasks` 从现有 `logs/gateway-*.log` 中的 `[定时任务]` JSON 记录聚合 11 项后台任务，包含启动续期补跑。没有新增任务调度模块、任务状态文件或持久化登记表；关闭 debug 仍会记录任务事件。
- 每条任务事件包含任务 ID、轮次 TraceID、进程 PID、开始/完成时间、执行结果和已知下次计划。只聚合当前进程启动后的记录，旧进程、损坏行不充当当前成功记录；没有记录时显示“无执行记录”。日志扫描预算为 16 MiB，达到预算会明确提示。
- 配置检查、凭据扫描、状态快照这三项高频任务，每 60 秒记录最近一次执行，实际变化/状态变化即时记录。任务页每 15 秒读取日志；周期性下次时间可按日志中的定时锚点推算，并标记“推算”，事件触发可能提前。一次性任务完成后不再安排下一次；过期且无法推算的计划等待新日志，不伪造执行结果。
- 网页凭据页和编辑器已移除，不再自动读取或展示完整凭据。原 `/admin/api/credentials` 与 `/admin/api/credential-edit` 后端接口暂保留兼容，仍受独立管理鉴权、同源、文件范围和版本冲突保护，网页不再调用。
- 网页标题及品牌文案使用「本地网关」，不再显示旧品牌名称；协议 Header、配置格式与数据字段保持兼容，不改写用户配置、日志或账号昵称中的原文。
- 「账号池」的「只显示可用账号」只保留状态为 `active` 且全局调度未停用的账号；「模型列表」的「只显示可用模型」只保留已启用且可用账号数大于 0 的模型。取消勾选可查看全部，筛选不改变调度、配置或历史统计。
- 两个筛选分别通过 Cookie 保存，刷新、退出再登录后恢复，默认不勾选。Cookie 只含 `0/1` 显示偏好，作用域为当前主机的 `/ui`，有效期一年，使用 `SameSite=Lax`，HTTPS 时加 `Secure`；Cookie 不保存任何 Key 或凭据，也不能用于登录。浏览器禁用 Cookie 时仍可筛选，但页面提示刷新可能无法记住状态。
- 「模型列表」国内 / 国际倍率后有 `!` 按钮，点击显示该倍率的**数据来源**、**更新时间**和一句**白话解释**（例如「官方接口给出的目录倍率」「官方促销已于 … 结束，接口仍返回 0.00x，该数值不可信」「上次真实探测结论：收费（尚未复测）」），其他来源按「其他记录」逐条给出一句解释。原始日志默认折叠在「原始日志（N 条，默认折叠）」里，需要时才展开，避免刷屏。
- 倍率无法确定具体数值（如「收费(倍率未知)」）时额外显示**如何刷新**：后台自动探测已关闭时提示「用该站点的账号请求一次这个模型，网关会按返回的 `usage.credit` 自动重新判定并写入日志」；探测已开启时提示会自动复测。该提示里的开关状态同样解析自普通日志（`[ModelPrice] 阶段=自动探测调度`），不是额外状态。
- 详情里**不显示「状态：未知」这类字样**：该结论本身是实测过的，写「未知」会让人误以为从未检测；实际含义由「上次真实探测结论：收费（尚未复测）」和「如何刷新」表达。
- 日志中完全没有该模型的记录时显示**没有日志**，并说明「用该站点的账号请求一次这个模型，就会产生新的倍率记录」，不猜测来源。
- 倍率来源只读 `GET /admin/api/rate-detail`（需管理 Key，仅支持 GET），复用定时任务页的日志读取方式：扫描 `logs/gateway-*.log` 尾部并解析，不新增调度器、状态文件或内存账本；结果缓存 20 秒，点击时按需拉取，不随总览轮询反复扫描。
- 解析的日志来源：`[Models] 官方倍率`（官方目录首次或变化时记录）、`[ModelPrice]`（探测结论，含缓存载入）、`[ModelCost]`（正常请求实测）。优先级与页面取值顺序一致：正常请求实测免费 > 探测免费 > 探测收费 > 促销过期 > 官方数值。
- 价格相关日志全部写入**普通日志**（`logs/gateway-YYYY-MM-DD.log`），不依赖 `debug.enabled`；调试日志关闭时这些记录仍然存在。日志只记录模型名、站点、倍率、credits、促销时间与账号文件名，不记录令牌。
- 「访问设置」可编辑 `gateway.apiPort` / `gateway.webPort`，保存调用原来的 `POST /admin/api/settings`。配置端口与实际监听端口分别显示，修改后**需重启网关**，不会直接中断当前页面或流式请求；显式 `-port` 仍优先于配置。
- 「配置」页点击「编辑配置」后先展示风险警告，确认后通过 `GET /admin/api/config-edit?acknowledged=1` 加载真实原文（包含 Key）；仅通过可信网络、HTTPS 或 SSH 转发使用。编辑器不把正文保存到浏览器存储，离开配置页、退出编辑或会话失效时清除原文，未保存修改需确认丢弃。
- 「校验并保存」通过 `POST /admin/api/config-edit` 提交 `content`、读取时的 SHA-256 `revision` 和 `acknowledged: true`。配置最大 1 MiB，必须是符合既有字段及类型规则的单个 JSON 对象；拒绝将 `[REDACTED]` 当作 Key。读取后被其他网页操作或服务器修改过的配置返回 `409`，不覆盖新版本；网页保留输入供核对，重新加载前提示丢弃未保存修改。
- 保存完整配置等效于直接修改服务器文件：可热配置立即生效，监听端口保持不变直到重启；日志保留规则可能触发不可撤销的删除。管理 Key 改变后退出旧会话、要求重新登录；清空管理 Key 需额外确认并提交 `confirmAdminKeyRemoval: true`，之后需在服务器本机重新设置。配置写入或热应用失败会尽力恢复旧文件，日志只记录阶段、结果和长度，不记录正文或 Key。
- 「日志」页通过 `GET/POST /admin/api/log-settings` 读写 `logs.retentionDays`，通过 `POST /admin/api/log-cleanup`（空 JSON 对象）清理过期日志，返回删除数量、回收字节、正在写入跳过数量与失败数量。
- 所有新接口均需要独立管理 Key，并复用同源校验和 TraceID 落盘审计；模型 API Key 不能编辑凭据、修改端口或清理日志。

- 未启用 `-webui` 时，管理端口不监听，`/ui` 与 `/admin/api/*` 也不注册路由。
- **管理 Key 的两种设置方式**（二选一即可）：
  1. **页面一键生成**：`adminKey` 为空时，在服务器本机、或用 SSH 本地端口转发（`ssh -L 8316:127.0.0.1:8316 用户@服务器`）后访问 `http://127.0.0.1:8316/ui/`，点击生成 32 字符随机 Key；Key 写入 `config.json` 并**仅在弹窗中展示一次**。远程（非本机）访问不能触发一键生成，避免他人抢先生成；但远程仍可用已设置好的 Key 登录。
   2. **手动编辑配置文件**：直接在服务器上编辑 `config.json`，把 `gateway.adminKey` 设为你自己的随机字符串（建议 32 位），保存后约 1 秒生效。此方式不需要本机访问，也不需要页面操作；登录时填写该字符串即可。
- `/admin/api/logs` 只允许读取 `logs/` 下命名受限的普通、调试、部署和前端审计日志，拒绝任意路径与目录穿越；返回日志先做秘密值脱敏，且单次读取有约 1 MiB 的扫描预算，超长单行会被省略。
- 前端为原生 HTML/CSS/JS，通过 `go:embed` 嵌入二进制，无额外构建步骤与运行时依赖；管理 Key 只保存在当前标签页的 `sessionStorage`，验证成功后才保存。
- 状态快照缺失或损坏时接口返回 `503`，页面保留上次数据并提示，不会把读取失败显示成零账号。

## 上游会话请求头（v1.14.20）

网关参照 WorkBuddy 官方客户端的会话／轮次／消息标识语义，为每次模型调用补齐
`X-Conversation-ID`、`X-Conversation-Request-ID`、`X-Conversation-Message-ID`。
国际站带工具声明的请求此前可能触发 `11128 conversation id missing`；这项兼容不关闭工具或思考，
也不改变提示词、输出预算和原有鉴权指纹。

- 三个协议入口（Chat Completions、Responses、Anthropic Messages）、流式与非流式聚合、
  国内与国际站都经过同一出站路径；手工 `probe` 和后台价格探测也有统一兜底。
- 优先采用客户端显式的 `X-Conversation-ID`（原样保留）；否则读取 `X-Session-ID`、
  请求顶层或 `metadata` 内的 `conversation_id`／`conversationId`／`session_id`／`sessionId`。
  合法 UUID 沿用；其他有效会话键按调用方隔离后规范化并生成稳定会话标识。过长或带控制字符的键忽略。
- `X-Conversation-Request-ID` 与 `X-Conversation-Message-ID` 可由客户端提供，
  也可通过顶层或 `metadata` 的同名下划线／驼峰字段提供；按 fork 的同组优先级补齐 trace/request 伙伴。
  有会话键而缺少会话请求 ID 时稳定派生，无会话键时独立生成；新生成消息 ID 为 32 位无连字符 UUID v7。
- 同一显式会话键的连续 HTTP 调用保持会话级 trace／conversation 标识稳定；
  同一个逻辑 HTTP 请求的安全网络重试、跨账号／站点回退复用本次解析出的完整 link IDs。
  每个新 HTTP 请求的 request/message/span 标识按 fork 的 `resolveLinkIDs` 规则生成并保持组内相等关系。
- 没有显式会话键时，每个 HTTP 调用独立生成会话，不会根据提示词、用户名或模型名猜测会话归属；
  这是本 fork 保留的取舍，不采用上游“每次重新生成轮次 ID”而破坏同会话 trace 稳定性的语义。
- 仅生成或规范化请求头，不记录原始会话键、请求正文或令牌；不向登录、续期、额度查询接口添加这些头。

## probe

免费 / 收费属性按「账号（含站点）+ 模型」学习，只有该账号真正请求过该模型才会写入账本。默认调度优先使用有余额账号，**余额耗尽的账号几乎不会被选中，也就学不到属性**。`probe` 用于主动补课。

> 注意：额度耗尽的账号会被上游整体拒绝（`14018 Credits exhausted`），此时连免费模型也会失败。要验证某模型是否免费，请使用**额度未耗尽**的账号。

```bash
# 探测全部账号，每个账号取模型目录前 5 个模型
workbuddy-gateway probe

# 只探测指定账号
workbuddy-gateway probe -auth workbuddy4.json

# 指定模型
workbuddy-gateway probe -auth workbuddy4.json -models hy3,deepseek-v4.1-flash

# 指定数量上限（默认 5，上限 50）
workbuddy-gateway probe -auth workbuddy4.json -limit 8
```

| 选项 | 默认 | 说明 |
|---|---|---|
| `-auth <path>` | 全部账号 | 只探测指定凭据（文件名或路径均可） |
| `-models <m1,m2>` | 目录前几个 | 指定要探测的模型 |
| `-limit <n>` | `5` | 未指定 `-models` 时探测的模型数量，上限 50 |

输出示例：

```text
正在请求 http://127.0.0.1:8317/admin/probe（账号=workbuddy4.json，模型=hy3）...

账号                   站点   模型     结果     credit  tokens  说明
workbuddy4.json        intl   hy3      paid     0.42    820     usage.credit=0.42，收费

汇总: paid=1
```

结果状态：

| 状态 | 含义 |
|---|---|
| `free` | `usage.credit=0` 且 `total_tokens ≥ 100`，已学习为免费 |
| `paid` | `usage.credit > 0`，已学习为收费 |
| `unknown` | 未返回 `credit`，或 `credit=0` 但样本过小 |
| `quota` | `14018` 额度耗尽，记为该账号该模型收费并阻断该模型 |
| `rate_limited` | `6004` 模型级限流，只冷却该模型 |
| `auth_failed` | 授权失效（probe 不会自动禁用账号） |
| `skipped` | 账号失效或无凭据 |
| `error` | 网络 / 协议错误 |

> 原理：`probe` 作为客户端调用运行中服务的 `/admin/probe`。账本保存在 `serve` 进程内存中，独立进程直接写状态文件会被服务快照覆盖，因此探测必须由运行中的服务执行。该接口仅接受回环来源；模型 API 启用 Key 校验时同样需要携带 `gateway.apiKey`。

## reset

清空**除登录凭据以外**的全部本地数据，并重新拉取模型与倍率。

```bash
workbuddy-gateway reset
```

清理范围：

- `workbuddy-status.json`（账号与模型状态快照）
- `wb-models-cache.json`（模型目录、倍率、价格探测结论）
- `*.disabled` / `*.json.disabled`（授权失效标记）
- `logs/`（运行日志）

保留：`workbuddy*.json` 登录凭据。

清理后会立即重新拉取模型目录与倍率。账号账本同时存在于 `serve` 进程内存中，若服务正在运行，请重启使其同步归零：

```bash
systemctl restart workbuddy-gateway
```

## 多账号池

三种配置方式：

```bash
# 方式一（推荐）：自动发现
# 把多个凭据文件放进工作目录，无需任何参数
workbuddy-gateway serve

# 方式二：-auth 逗号分隔
workbuddy-gateway serve -auth workbuddy.json,workbuddy2.json

# 方式三：-auth-dir 目录
workbuddy-gateway serve -auth-dir ./auths
```

行为说明：

- **轮询**：请求按 round-robin 在可用账号间分发。
- **429 冷却**：`6004` 只冷却触发模型；无法归因到模型的 429 才进入账号级冷却，冷却到期自动恢复。
- **授权失效**：401/403 类错误禁用账号并删除凭据文件，同时写 `*.disabled` 标记；重新 `login` 后自动恢复。
- **额度耗尽**：`剩余=0` 标记「付费耗尽」，仍可服务已确认免费的模型。
- **热加载**：默认每 5 秒扫描，新增 / 更新 / 删除凭据免重启。
- **串行化**：同一账号请求严格排队，避免并发双发触发风控；不同账号可并行。

## 模型列表与倍率

**列表来源**：实时接口 `GET {Base}/v2/enterprises/personal/models` 与 npm 包静态目录，按模型 ID 去重、**接口优先**。

```text
两路都成功  → 合并去重
一路成功    → 使用成功那路
两路都失败  → 使用本地缓存 wb-models-cache.json
失败且无缓存→ 该站点本轮不展示模型（不影响模型调用）
```

**免费站点优先**：若某模型出现「一个站点免费、另一个站点收费」，调度优先使用免费站点的账号，直到该站点账号全部不可用（冷却 / 耗尽 / 失效）才回退到另一站点；若两个站点都免费或都收费（只是倍率不同），则不设优先，保持正常轮询。

**倍率**：

```text
1. 促销生效中：生效倍率 = credits × factor（factor=0 → 0.00x）
2. 促销已过期：接口 credits 不可信（上游常把促销价固化进 credits），
   探测出结果前显示 -，随后由实测决定
3. 模型不在接口目录中：同样交由实测决定
4. 无促销且 credits 有值：直接展示该倍率
```

**价格探测（默认关闭）**：仅显式传入 `-allow-price-probes` 才开启后台探测，优先选择有余额的同站点账号，余额未知时也可能使用。它会发起真实生成请求（`max_tokens=300`），可能消耗积分；频率 / 批量限制不等于积分预算，目前没有累计积分消耗上限。

默认关闭只影响后台主动探测：目录刷新照常获取官方价格及促销时间；正常客户端请求照常根据 `usage.credit` 学习收费 / 免费（零积分且总 token 数至少 100 才认定免费）。显式 `probe` 命令仍可主动实测，同样可能消耗积分。

```text
探测免费 → 展示 0.00x；仍符合候选条件时，至少间隔 12 小时复测
探测收费 → 展示 收费(倍率未知)；仍符合候选条件时也可能再次探测
14018 / 无 usage.credit / 样本过小 → 不覆盖，保持未知
```

探测调度（仅显式开启后生效）：

| 时机 | 说明 |
|---|---|
| 服务启动 | 启动后约 20 秒执行首轮 |
| 首次 / 重置后 | 单轮最多 30 个，快速补齐结论 |
| 收敛后 | 单轮最多 5 个，每模型 12 小时最多一次 |
| 待探测未清空 | 用 2 分钟短间隔追赶，清空后回到 30 分钟 |
| 目录刷新成功 | 立即触发一轮 |
| 凭据变化 | 立即触发一轮（含「原本没有某站点账号、后来加入」的情况） |

仅探测被实际请求过、或接口明确需要确认的模型，避免无谓消耗额度。

`/v1/models` 响应头 `X-Model-Source` 与 `/health` 的 `model_source` 会标注目录来源。

### 模型能力扩展字段

`/v1/models` 的每条模型在目录确有可信数据时会附带能力字段；**未知一律省略，不做 1M 之类兜底**，避免下游按错误窗口预留上下文：

| 字段 | 含义 |
|---|---|
| `context_length` | **模型能力上限**，取上游 `maxInputTokens`（缺失时回落 `maxAllowedSize`）。决定上游接受多少输入。 |
| `max_output_tokens` | 输出上限，取上游 `maxOutputTokens`。 |
| `default_context_length` | **客户端默认预算**，取上游 `contextWindow.defaultLength`。它只决定客户端自己从多少 token 开始压缩，**不是**能力上限。 |
| `context_length_options` | 客户端可选档位，取上游 `contextWindow.supportedLengths`（≥2 档才给出，升序）。 |
| `capabilities_by_site` | 仅当国内站与国际站对同一模型的声明不一致时给出，按站点列出上面四个字段。 |

要点：

- `context_length`（能力上限）与 `default_context_length`（默认预算）语义不同，必须分开看。以 `deepseek-v4.1-flash` 为例：上限 1000000、默认预算 300000、可选档位 300000 / 600000 / 1000000。
- 同名模型可能由国内站或国际站账号分别服务，能力不一定相同。**不一致时不取最大值冒充**：顶层标量留空，改为在 `capabilities_by_site` 给出分站点明细，避免下游按较大值预留而实际被路由到较小窗口的账号。
- 这些字段只描述能力，**不注入上游请求参数、不截断消息，也不改变现有输出预算（`max_tokens`）逻辑**。客户端实际发多少上下文，仍由客户端自己的压缩策略决定。
- 目录刷新时日志会输出一条 `[模型能力]` 覆盖统计（各站点有上限／有档位／有输出上限的模型数），便于核对哪些模型缺数据。

## 用量与性能统计（stats.json）

网关在**程序工作目录**维护一份可选的 `stats.json`，记录按凭据分组的用量事实，供网页控制台「总览」页展示。

### 记录内容

| 内容 | 说明 |
|---|---|
| 账号模型账本 | 每个凭据的 `ModelStates`（按模型隔离的成本、额度阻断、冷却、最近观测时间），键由「凭据文件 + 站点 + UID + 企业 ID」派生 |
| 逐次账号调用 | 完成时间、模型、HTTP 状态、是否完整、输入／输出／总 Token、缓存读取、`usage.credit`、总耗时、首字耗时 |

**不记录**：访问令牌、刷新令牌、请求或响应正文、提示词、账号昵称。

### 统计口径

- **按实际上游账号调用统计**：一次请求触发多次账号调用（失败重试、额度耗尽换号）时，每个被调用的账号各记一条。未选到账号就被拒绝的请求（鉴权失败、参数错误、模型被禁用）不计入任何账号。
- **积分只取 `usage.credit`**，不用「账号余额差」推算，避免把并发请求和额度刷新算成消耗。
- **缺失的 usage 记为空样本，不是零消耗**：接口返回 `—` 和「Token 1/2 请求有样本」这样的覆盖数，0 与未知可以区分。
- **缓存读取已包含在输入 Token 内**，单独展示但不重复累加。
- **首 Token 耗时（TTFT v2）**：从网关请求入口开始，到解析出首个非空文本、推理或有效工具调用增量结束；心跳、角色声明、空内容、usage、finish、DONE 不计入。工具名称或非空参数增量计入，单独工具 ID 不计入。三个协议的流式／非流式、普通日志、CLI 与网页使用同一测量结果，截断或取消的请求不进入 TTFT 平均。
- **完整性判定**：只由上游流本身决定——读取出错或没有结束原因都不计；已确认完整结束后，客户端收到 `[DONE]` 就断开连接属于正常行为，不再因为事后看到请求 Context 已取消而丢弃该次首 Token 样本（v1.14.9 修复）。
- **与 dsh 的边界**：采用相同的有效增量判据，但网关起点是收到 HTTP 请求（拿不到 dsh 的 `step/start`），无法计入客户端前置耗时；网关仍按所选时间／账号／模型汇总所有调用，包括辅助请求，不是 dsh 单个会话的平均。非流式时测量上游生成的首 Token，而非客户端收到完整 JSON 的时刻。
- **历史兼容**：新请求记录带 `ttftMetric: "first_token_v2"`。旧记录的首响应体耗时保留但不参与新 TTFT 平均；Token、积分和历史总耗时仍正常汇总，网页显示被排除的旧口径样本数。新记录的总耗时也以网关请求入口计时，避免排队后出现首Token比总耗时更大的口径冲突。
- 时间维度按 **UTC+8 日历**：小时对齐整点，**周从周一开始**，月按自然月。请求耗时图里柱形是首 Token、折线是总耗时，每个模型各自一条柱和一条线，只平均该模型自己的调用，不把不同模型合成一条。某个模型在某个时间桶没有调用时，它的柱和线都**断开**，不画成 0。上方摘要卡里的平均总耗时和平均首 Token 仍是当前范围内全部调用的平均值。
- **只统计本功能启用后的请求**，不回溯历史日志，也不补造数据。

### 网页总览页

「总览」页最上面是**运行状态**（账号池健康度与账号日志告警），再往下是「用量与性能」：可选**统计粒度**（小时／日／周／月）、**统计范围**（全局或单个凭据）、起止日期；展示总 Token、总积分、账号调用次数、平均总耗时、平均首字五张摘要卡，两张组合图（用量趋势：Token 折线＋积分柱形、左右双轴；请求耗时趋势：总耗时折线＋首 Token 柱形，均按模型分开），以及一张**模型用量排名**表。

排名表与图表使用同一套时间范围和账号过滤：只列出所选范围内**确实有调用**的模型，按总 Token 降序排列（Token 未知时按请求数降序），用量最多的排第一；没有调用的模型不出现。表内同时给出请求数、完整／失败、输入／输出、缓存读取、积分、平均耗时、平均首字与数据覆盖数。

图表为页面内原生 SVG，不加载任何外部图表库。用量图把 Token（折线，左轴）和积分（柱形，右轴）放在同一张图里，两者量级不同所以分左右刻度。耗时图的柱形是首 Token、折线是总耗时；图例与排名表使用同一批模型，并跟随当前时间和账号范围，没有调用的模型不画。时间桶没有该模型、该指标的样本时不画点也不画柱，不补成 0。

### 总览运行状态：健康度与账号日志告警

运行状态区域不再重复展示账号数量和分站点数量卡片，改为左侧健康度、右侧日志告警；账号池页继续保留详细状态。该区块已移到总览最上面：先看健康度与告警，再看用量与性能。

- **健康度 = 可用且未全局停用的账号 / 账号池全部账号 × 100%**。主动停用的账号仍在分母内；全部可用显示 `100%`，部分可用向下保留一位小数。无账号或状态快照过旧时显示 `—`，不伪装成全健康。
- 健康度描述账号级状态，不是某个模型的可调用率；单模型冷却不等同于整个账号失效。
- 告警来自 `logs/gateway-YYYY-MM-DD.log`，兼容既有冷却/额度耗尽/失效/停用日志，并增加 `[账号状态]` 结构化记录。仅在启动或状态变化时记录，包含 TraceID，不写凭据、Token 或上游错误正文。
- 只显示**当前快照仍异常且找到对应日志**的记录，同账号同类别去重；恢复后的历史异常不继续显示。找不到日志时会提示缺失，不编造记录。
- 告警按**日志时间倒序，最新在上**；严重程度只用于颜色和标签，不影响位置。时间相同按账号文件名、告警类别稳定排序。
- 恢复后自动消除的是对应的异常类别，不是删除该账号所有告警。例如额度恢复但账号仍被手动停用时，仅移除「积分用尽」，保留「账号停用」。这不是即时推送：快照和总览通常各约 3 秒刷新；额度恢复还需先被后台额度查询发现（默认每 5 分钟查询一轮）。日志扫描缓存 10 秒不阻止用最新快照剔除已恢复项；网络或读取失败时会保留旧结果并提示。
- 严重程度：红色「紧急」= 账号失效；橙色「重要」= 账号过期、积分用尽；黄色「注意」= 账号冷却；蓝灰色「提示」= 主动停用。颜色之外还有文字标签。
- 日志读取总预算 4 MiB，扫描结果短缓存 10 秒，列表最多 100 条。达到范围上限或日志缺失时给出提示；日志读取失败保留旧列表并标明失败，不影响健康度查询或模型调用。
- `/admin/api/account-alerts` 只读且需要管理 Key，不能通过该接口改变账号状态。

### 鲁棒性

- `stats.json` **不存在时静默从空统计启动**，首次有数据后自动尝试落盘。
- **无法写入**（权限不足、磁盘满、路径被占用）时降级为「仅内存」：继续统计和展示，网页显示「仅内存 · 未落盘」，后台每 5 秒自动重试，**不阻塞、不中断模型请求**。
- **文件损坏或不是普通文件**（例如被替换成符号链接或目录）时**保留原文件不覆盖**，同样降级为仅内存，避免把用户数据覆盖掉。
- 落盘采用「同目录临时文件 → `fsync` → 原子重命名」，权限 `0600`；进程收到停止信号时会先冲刷一次。
- 文件有安全大小上限；超出后停止写入并保留内存统计。

## 思考等级传参

网关对外暴露的是 **OpenAI 兼容**的思考等级参数，无论下游客户端来自哪个 agent 生态，都按 OpenAI 规范传参即可；网关负责翻译成上游认识的扁平字段。

| 入口 | 客户端可传（OpenAI 兼容） | 上游实际收到 |
|---|---|---|
| `POST /v1/chat/completions` | 顶层 `reasoning_effort` | 扁平 `reasoning_effort` |
| `POST /v1/chat/completions` | 嵌套 `reasoning.effort` / `reasoning.summary`、`text.verbosity` | 扁平 `reasoning_effort` / `reasoning_summary` / `verbosity` |
| `POST /v1/responses` | `reasoning.effort` / `reasoning.summary`、`text.verbosity` | 同上（由网关摊平） |

归一化规则：

| 输入 | 处理 | 说明 |
|---|---|---|
| `none` / `off` / `disabled` / `""` / `null` | 删除字段 | 语义为关闭推理 |
| `auto` / `default` | 删除字段 | 交由上游按模型默认档位决定 |
| 其他非空字符串 | 转小写、去空白后原样转发 | 如 `HIGH` → `high`、`" high "` → `high` |
| 未传 | 不发送 | **绝不注入** |

档位取值本身不做白名单校验——各模型支持的档位由上游裁决（不支持时返回 `11150 not supported by the current model`）。常见取值：`minimal` / `low` / `medium` / `high` / `xhigh` / `max`。

> **为什么不注入**：官方客户端发往同一上游（`www.workbuddy.ai`）的报文不含 `reasoning_summary`，且强行注入思考字段会触发上游内容安全拦截（`code 11102` / `11128`）。网关因此只做「客户端显式传参 → 归一化转发」，不凭空补字段。

### 上游字段语义（实测）

以下为对 `https://www.workbuddy.ai/v2/chat/completions` 的实测结论（`stream` 必须为 `true`，非流式一律 `code 11101`）：

| 字段 | 上游行为 |
|---|---|
| `reasoning_effort`（扁平） | 唯一生效的思考开关。取值大小写/空白敏感，`HIGH`、`" high "` 均 `400 11150`；`off` / `disabled` / `auto` 同样 `11150`。`none` 被接受但**仍开启推理**（prompt_tokens 18→43），与 OpenAI「不推理」语义相反，故网关将其归一化为删除字段。 |
| `reasoning.effort`（嵌套） | **被完全忽略**（推理根本不开启），因此网关必须摊平。 |
| `reasoning_summary`（扁平） | 上游不校验取值（`auto` / `concise` / `detailed` / `bogus` / `none` / `null` 均 `200`），原样透传，网关不改写其取值。 |
| `verbosity`（扁平） | 上游不校验取值，与推理开关正交（无 `reasoning_effort` 时也接受）。 |
| `max_thinking_tokens` | 上游接受（`MAX_THINKING_TOKENS` 环境变量经客户端设置），网关透传。 |

## 客户端指纹对齐

网关向上游发起请求时，会按账号所属站点逐项对齐官方客户端的请求头，避免因自造字段或缺失字段形成可静态识别的机器特征。

两套基线来自两次安装抓包：

- **国内站**：**本机 5.5.3 客户端**（`D:\workbuddy` 安装，productName `WorkBuddy`，内置 CLI 包版本 **2.137.1**）的 bundled CLI 被按宿主方式驱动（注入宿主 `CLIENT_INFO_*` + 指向本地 sink 的 `product.json`）后的线上字节抓包（`.client_ref/cap/cn_chat_capture.jsonl`，6 条请求：模型请求 1 条 + `/v3/config`、`/v2/report` 控制面族）。`X-IDE-Type` / `X-IDE-Name` / `X-IDE-Version` 为 `WorkBuddy` / `WorkBuddy` / `5.5.3`，UA 为 `WorkBuddy/5.5.3 WorkBuddy/5.5.3 CLI/2.137.1`；模型请求体 gzip 压缩（`Content-Encoding: gzip`），且模型请求与控制面请求**都不发送** `Accept-Encoding`（`Host` / `Content-Length` 齐备，故该缺席是线上实测而非钩子层级盲区）。

> 国内站旧基线（桌面宿主 5.5.2，`X-IDE-*` = `CodeBuddy` / `5.5.2`，UA `…/5.5.2 CLI/2.137.1`）来自一次 5.5.2 桌面宿主抓包中宿主侧注入的 `CodeBuddy` 自述。本机 5.5.3 安装在磁盘上的 `@genie/workbuddy-desktop` 5.5.3 的 `main/client-info-env` 模块算出的注入值是 `CLIENT_INFO_PLATFORM = WORKBUDDY_PLATFORM = "WorkBuddy"`、`CLIENT_INFO_IDE_TYPE = "WorkBuddy"`、`CLIENT_INFO_PLATFORM_VERSION / PRODUCT_VERSION / PLUGIN_VERSION = app.getVersion() = "5.5.3"`、`CLIENT_INFO_USER_AGENT_EXTENSION = "CLI/2.137.1"`（对应 `.client_ref/cn/main__client-info-env.js`、`.client_ref/cn/main__workbuddy-product-config.js`），与 5.5.3 客户端的实发抓包逐字一致。网关按**实测实发**对齐 —— 风控判定的是线上字节，不是源码里的分支。
- **国际站**：桌面宿主 **5.7.6**（内置 CLI 包版本 **2.156.0**）驱动其 bundled CLI 直连 `www.workbuddy.ai` 的抓包。桌面宿主以 `CLIENT_INFO_*` 环境变量注入身份（`buildWorkbuddyClientInfoEnv`）：`CLIENT_INFO_PLATFORM` / `CLIENT_INFO_IDE_TYPE` 为 `WorkBuddy`，`CLIENT_INFO_PLATFORM_VERSION` / `PRODUCT_VERSION` / `PLUGIN_VERSION` 为 `app.getVersion()`（`5.7.6`），`CLIENT_INFO_USER_AGENT_EXTENSION` 为 `CLI/2.156.0`。故 `X-IDE-Type` / `X-IDE-Name` / `X-IDE-Version` 为 `WorkBuddy` / `WorkBuddy` / `5.7.6`，UA 为 `WorkBuddy/5.7.6 WorkBuddy AI/5.7.6 CLI/2.156.0`。

> 旧版本曾以「CLI 直连」的裸 CLI 身份（`X-IDE-*` = `CLI`、UA = `CLI/2.137.1 WorkBuddy AI/2.137.1`）作为国际站基线。真实国际版客户端是**桌面宿主 + 内置 CLI**，裸 CLI 身份与之不符：宿主不会发送 `CLI/CLI` 的 `X-IDE-*`，而会注入自己的产品标识。

> 运行时版本也随宿主走：宿主以 `ELECTRON_RUN_AS_NODE=1` 用自带 Electron 二进制启动 CLI，故 `x-stainless-runtime-version` 是 Electron 内置 Node 的版本，不是系统 Node 版本。本机 5.5.3（国内站）与 5.7.6（国际站）两个桌面客户端实发值都是 `v22.21.1`（本次两次抓包各自实测：`upstreamProfile.NodeVersion`），5.5.2 那份旧抓包的 `v22.22.2` 已被取代 —— 本机两个客户端自带的 Electron 内置 Node 均为 `v22.21.1`（即 Electron 37 系），故两站同值。

**对齐基线**：国际站官方客户端发往 `/v2/chat/completions` 的真实请求头（线上字节抓包实测，共 39 项，含传输层头）。

### 三套头集合：模型请求 / 控制面 / 守护进程

客户端用**三套** HTTP 栈，头集合互不相同，照搬任一套去发另一套的请求都会同时产生「多出对方没有的头」与「缺失对方必带的头」两类偏差：

| 家族 | 栈 | 覆盖的请求 |
|---|---|---|
| 模型请求 | bundled OpenAI Node SDK + 自建头表（`backendHeaders`） | `/v2/chat/completions` |
| 控制面 | axios 实例 `RestOperations`（`controlHeaders`） | 登录/续期、账号快照、控制台计费探测 |
| 守护进程 | Node 全局 fetch = undici（`daemonHeaders`） | `/v2/enterprises/personal/models` |

依据是 bundled CLI 2.156.0 的 `dist/codebuddy-lite-wb.mjs` 源码（登录链路四步逐字提取）+ 桌面客户端对 `GET /v2/plugin/accounts` 的实发请求（抓包）：

| 步骤 | 请求 | 头集合（源码） |
|---|---|---|
| `fetchAuthState` | `POST /v2/plugin/auth/state?platform=<authentication.attributes.platform ?? platform>` | `enterpriseHeaders()`（`X-Domain`= `URI.parse(endpoint).authority`）+ `traceSpan.requestHeaders` + `X-No-Authorization` / `X-No-User-Id` / `X-No-Enterprise-Id` / `X-No-Department-Info` |
| `loopGetToken` | `GET /v2/plugin/auth/token?state=…` | `traceSpan.requestHeaders` + 同上四项 `X-No-*`（**无** `X-Domain`） |
| `loopGetAccount` | `GET /v2/plugin/login/account?state=…` | `enterpriseHeaders(token)`（`X-Domain`= token 的 `domain`）+ `Authorization: Bearer …` + `traceSpan.requestHeaders` + `X-No-User-Id` / `X-No-Enterprise-Id` / `X-No-Department-Info`（**无** `X-No-Authorization`） |
| `refreshSession` | `POST /v2/plugin/auth/token/refresh` | `enterpriseHeaders(auth)` + `X-Refresh-Token` + `X-Auth-Refresh-Source: plugin` + `traceSpan.requestHeaders`（再由 `AuthenticationHttpInterceptor` 补 `Authorization` / `X-User-Id` / `X-Enterprise-Id` / `X-Tenant-Id`） |

网关自身的三个**控制台计费探测**（额度摘要 `/billing/meter/get-user-resource-summary`、套餐资源 `/billing/meter/get-user-resource`、每日签到 `/v2/billing/meter/daily-checkin`）同属控制面：客户端由同一 axios 实例发出（`BackendProvider.fetchResourceSummary` / `fetchResourcePackagesPage`、`checkin()` 的 `billingPrefix = /v2`），故一律走 `controlHeaders`。旧实现这三处混用模型请求头集合（`X-IDE-*` / `x-stainless-*` / `x-codebuddy-request` / `X-Agent-*`）并自造 `X-Client-Platform: web` —— 即网关自己造出了官方客户端不可能产生的头组合。签到接口在官方客户端还额外携带 `X-Device-Token`（Turing 设备令牌，来自本地原生风控 SDK），网关无该 SDK，**不臆造该头**。

**守护进程家族**（`/v2/enterprises/personal/models`，网关的实时模型目录来源）：桌面宿主把 `serverFetch = (e,t) => fetch(e,t)` 注入守护进程（`main/index.js`），即走 Node 全局 fetch（undici），头表为 `main/server.js` 的 `buildAuthHeaders`：

```js
{Accept:"application/json", Authorization:`Bearer ${auth.accessToken}`,
 X-User-Id, X-Enterprise-Id, X-Tenant-Id, X-Domain,
 "X-B3-TraceId", "X-B3-SpanId", "X-B3-Sampled":"1", "X-Trace-Id", b3:`${trace}-${span}-1`}
// 再经 injectRequestId 补 X-Request-ID = X-Trace-Id ?? randomBytes(16).hex
```

自动化头不是 axios 那套：客户端实际运行时（Electron 37.10.3 / Node 22.21.1 / undici **6.22.0**，以 `ELECTRON_RUN_AS_NODE=1` 直接实测获得的线上头）为 `user-agent: node`、`accept-encoding: gzip, deflate`、`accept-language: *`、`sec-fetch-mode: cors`、`connection: keep-alive`。旧实现复用模型请求头集合，等于往守护进程接口上发了带 `X-IDE-*` / `x-stainless-*` / `traceparent` 的请求。

| | 模型请求 | 控制面请求 | 守护进程请求 |
|---|---|---|---|
| `Accept` | `application/json` | `application/json, text/plain, */*`（axios 默认） | `application/json` |
| `Content-Type` | `application/json`（请求带 body 才发送） | `application/json`（**仅带 body 的步骤**：`auth/state`、`refreshSession`、额度/套餐/签到探测；`auth/token` 轮询与 `login/account` 是 GET，**不发送**） | **不发送**（`includeJsonContentType: false`） |
| `Accept-Encoding` | 国际站 `gzip, compress, deflate, br`；国内站不发送 | 国际站同左；国内站不发送 | `gzip, deflate`（undici 自动，全小写键名） |
| `X-Requested-With` | `XMLHttpRequest`（小写键名 `x-requested-with`） | `X-Requested-With`（规范化大小写） | **不发送** |
| `X-IDE-*` / `X-Agent-*` / `X-Conversation-*` / `x-stainless-*` | 发送 | **不发送** | **不发送** |
| `X-Product` | 发送 | 发送（`ProductEndpointHttpInterceptor` 对每个请求注入） | **不发送** |
| `User-Agent` | 站点 Profile UA（`WorkBuddy/5.7.6 … CLI/2.156.0`） | 同左 | `node`（undici 自动） |
| `b3` | 四段 `${trace}-${span}-1-` | 四段 `${trace}-${span}-1-` | **三段** `${trace}-${span}-1` |
| 链路头键名 | `X-Trace-ID` / `X-Request-ID` | `X-Trace-ID` / `X-Request-ID` | `X-Trace-Id` / `X-Request-ID` |
| 其他传输层头 | `traceparent` + `X-B3-*` + `Connection: keep-alive`（末位） | 无 `traceparent` | `sec-fetch-mode: cors`、`accept-language: *`、`connection: keep-alive` |

`User-Agent` 在小写键名上有个 Go 侧实现细节：`transport` 只在 `Header` 中存在**规范化键** `User-Agent` 时才采用其值，否则回退 `Go-http-client/1.1`；故 `daemonHeaders` 把规范化键置空（transport 视为「显式不发送」）再写入小写 `user-agent`，使线上只剩 `user-agent: node`。

网关据此拆成 `commonHeaders`（两端通用）、`backendHeaders`（模型请求）、`controlHeaders`（控制面）、`daemonHeaders`（守护进程 fetch 家族）。压缩协商按站点与家族区分，国内站模型与控制面不发送 `Accept-Encoding`；`transport.DisableCompression` 阻止 Go 自行补头或接管解压。所有响应统一由 `wrapUpstreamDecoding` 解压：`gzip` / `deflate` 用标准库、`br` 用纯 Go 的 `andybalholm/brotli`，不支持的编码明确报错（历史实测控制面 `auth/state` / `auth/token/refresh` / `login/account` 返回未压缩响应，分别为 241 / 101 / 251 字节）。

### 响应解压（国际站模型请求声明 `Accept-Encoding`）

上一版本把模型请求的 `Accept-Encoding` 列为**唯一的主动偏差**（客户端发送、网关不发送），本版本消除它。

- **客户端实际行为**：模型请求线上字节带 `Accept-Encoding: gzip, compress, deflate, br`（值来自 axios 默认头，由 Node http 适配器在传输层补写）。依据是仓库内的线上字节抓包：`.client_ref/cap/intl_chat_capture.jsonl`（5 次模型请求）与 `intl_toolturn_capture.jsonl`（72 次模型请求），每条模型请求 39 个头，该头位于第 36 槽（0 基），即 `Content-Length` 与 `Host` 之间。更早的抓包（`.client_ref/capture2.jsonl` 等，模型请求 38 个头）没有该头，因为那批钩在 Node `https.request` / 头部对象层，看不到适配器后补的传输层头；钩子层以上得到的头**集合**与**顺序**结论不受影响。
- **网关据此声明同一值**：`backendHeaders` 补上该头，`wireorder.go` 的顺序基线相应加入该槽位（`Content-Length → Accept-Encoding → Host → Connection`）。
- **响应侧自行解压**：`gzip` / `deflate` 用标准库，`br` 用纯 Go 的 `andybalholm/brotli`（新增依赖，无 CGO，不影响 9 目标交叉编译）。多段编码（RFC 9110）按声明**逆序**解码；未支持的编码（如 `zstd`）返回 `502 upstream_encoding_unsupported`，绝不把压缩字节当明文交给下游。解压层包在空闲看门狗**外侧**：卡死判定仍按原始字节的到达节奏，下游与聚合逻辑始终读到明文 SSE。
- **错误响应一并解压**：上游的非 2xx 响应同样可能被压缩，而 `isQuotaExhausted` / `isRateLimited` / `isAuthFailure` 的判定与日志都依赖正文关键字 —— 拿压缩字节去判定会让限流/额度/鉴权错误降级成「未知错误」。故错误分支改为与成功路径同一套解压（`readDecodedAll`）。
- 抓包只记录请求侧头部，**上游是否真的以 `br` 压缩模型响应流未获确认**；实现不依赖该假设，四种响应形态都能正确落地。

### 关键结论与依据

| 项目 | 处理方式 | 依据 |
|---|---|---|
| `X-Client-ID` / `X-Client-Version` | **移除** | 客户端全量安装目录（含 `app.asar`）字节级 0 命中；旧值 `codebuddy-cli` / `2.143.1` 属网关自造 |
| `X-Client-Platform` | **移除** | 客户端全量安装目录字节级 0 命中（旧值 `web` 属网关自造）；原仅出现在额度与签到两个控制台探测上，与模型请求头集合叠加后形成客户端不可能发出的组合 |
| `Origin` / `Referer` | **移除** | Node/Electron 运行时无浏览器语义，客户端实测不发送；发送反而是不一致特征 |
| `Accept` | `application/json`（单一值） | 客户端实测非浏览器默认的 `*/*` 列表 |
| `User-Agent` | 国际站 `WorkBuddy/5.7.6 WorkBuddy AI/5.7.6 CLI/2.156.0`；国内站 `WorkBuddy/5.5.3 WorkBuddy/5.5.3 CLI/2.137.1` | 模型请求由桌面宿主的 `WorkbuddyUserAgentHttpInterceptor` 生成：`${applicationName}/${productVersion} ${platform}/${platformVersion} CLI/${cliVersion}`。两站的 `applicationName` = `platform` = `WorkBuddy`、`productName` = `WorkBuddy AI`、`productVersion` = Electron `app.getVersion()`（国际站 5.7.6 / 国内站 5.5.3，均实测）。国内站旧值 `WorkBuddy AI/5.5.2` 来自 5.5.2 抓包时的宿主注入，本机 5.5.3 实发已是 `WorkBuddy/5.5.3` |
| `X-IDE-Type` / `X-IDE-Name` / `X-IDE-Version` | 国际站 `WorkBuddy` / `WorkBuddy` / `5.7.6`；国内站 `WorkBuddy` / `WorkBuddy` / `5.5.3` | 客户端取 `telemetryClientInfo`，缺失时回退宿主注入的 `clientInfo.ideType` / `platform` / `platformVersion`；两站的注入值都由宿主的 `client-info-env` 模块算出（国内站 5.5.3 磁盘源码：`.client_ref/cn/main__client-info-env.js` 的 `WORKBUDDY_PLATFORM = "WorkBuddy"` + `app.getVersion()`），与线上实发一致（`.client_ref/cap/cn_chat_capture.jsonl`）。旧值 `CodeBuddy` / `5.5.2` 来自 5.5.2 桌面宿主抓包，未被本机 5.5.3 实发复现 |
| `X-Request-ID` | 32 位小写 hex，每请求唯一，**UUID v7 形态**（版本位 `7`，前 48 位为毫秒时间戳） | 客户端 `uuidv7().replace(/-/g,"")`（bundled CLI 依赖 `uuidv7@^1.2.1`，源码 `nH: () => uuidv7`） |
| `X-Trace-ID` | 与 `X-Request-ID` **解耦**，为 OTel traceId（全链路同值） | 实测 `X-Trace-ID` == `traceparent` 的 traceId，且同一 session 内稳定 |
| `traceparent` / `b3` / `X-B3-*` | 补齐（OTel + B3 双份） | 客户端同时发送两套传播头 |
| `X-Conversation-*` / `X-Root-Request-ID` / `X-Agent-*` | 补齐 | 客户端会话与 Agent 语义骨架，缺失即特征 |
| `x-stainless-*` | 合成（6 项固定 + 1 项按站点取值，**全小写键名**），`x-stainless-runtime-version` 两站均为 `v22.21.1`（`upstreamProfile.NodeVersion`，各自抓包实测） | 客户端 chat 请求由 bundled OpenAI Node SDK 发出，上游始终可见该指纹族；网关用 Go `net/http` 发起，不合成即为缺失。SDK 以全小写发出该族头。**不透传下游的 `x-stainless-*` / `User-Agent`**：第三方下游（Claude Code 等）会带自己的 SDK 版本与 UA，与 WorkBuddy 的 IDE 头构成官方客户端不可能产生的组合。`x-stainless-runtime-version` 是**运行 SDK 的 Node 版本**：桌面宿主以 `ELECTRON_RUN_AS_NODE=1` 用自带 Electron 二进制启动 CLI（源码 `buildBaseEnv`），故取 Electron 内置 Node 版本 —— 本机 5.5.3（国内站）与 5.7.6（国际站）两个宿主实发均为 `v22.21.1`；5.5.2 旧抓包的 `v22.22.2` 已被取代 |
| `Accept-Encoding` | **国际站模型与控制面**发 `gzip, compress, deflate, br`；**国内站模型与控制面均不发**；响应仍统一解压 | 国际站 `.client_ref/cap/intl_chat_capture.jsonl` / `intl_toolturn_capture.jsonl`（5 + 72 次，39 个头）第 36 槽是该头；国际站控制面来自桌面客户端 `GET /v2/plugin/accounts` 实测。国内站 `.client_ref/cap/cn_chat_capture.jsonl` 的模型请求、`/v3/config`、`/v2/report` 均不带该头（sink 侧 `Host` / `Content-Length` 齐备，不是钩子盲区），两站不能写成一套 |
| `X-No-*` | 仅未鉴权时成组发送，值 `"true"` | 实测两种形态：已鉴权（`Authorization`+`X-User-Id`+`X-Domain`+`X-Product`，无任何 `X-No-*`）；未鉴权仅 `X-No-*` |
| `X-Refresh-Token` | 仅刷新链路发送，chat 不发送 | 客户端源码中该头只出现在 `auth/token/refresh` 与 `account/switch` 调用 |
| `X-Auth-Refresh-Source` | 刷新链路发送 `plugin` | 旧值 `workbuddy` 属网关自造；客户端 `refreshSession` 实测为 `plugin` |
| `X-Tenant-Id` | 与 `X-Enterprise-Id` 同值，仅企业账号发送 | `AuthenticationHttpInterceptor` 在账号存在 `enterpriseId` 时无条件补该头（同一分支里 `X-No-Enterprise-Id` 只拦 `X-Enterprise-Id`，不拦 `X-Tenant-Id`） |
| `x-codebuddy-request` | **合成 `"1"`**，客户端自带时透传 | 客户端对模型请求恒发送该头（源码 `withSecurityHeader` 注入；桌面宿主 `daemon-bootstrap` 的模型请求构造器亦显式 `set`），CLI 直连与桌面宿主两条链路、含非回环目标均携带 |
| `Content-Encoding` | **两站**模型请求体均 gzip 压缩（`Content-Encoding: gzip`，与体积无关） | 客户端 `GzipRequestProcessor`（处理器链 `priority=9999`）对模型请求体统一压缩：`product.json` 的 `features.RequestBodyGzip = true`。国内站旧结论「保持不压缩」是本 fork 早期未实测该站点所致；本机 5.5.3 国内站链路抓包实测请求体带 gzip 魔数与 `Content-Encoding: gzip`（`.client_ref/cap/cn_chat_capture.jsonl`），故两站一律压缩 |
| `Connection` | 模型请求与守护进程请求发送 `keep-alive` | 客户端由 Node http 模块补齐（模型请求实测恒在头部块末位），Go transport 默认不写；缺失即为可识别偏差 |

### 字节级对齐（v1.8.4 新增）

「头集合一致」不等于「字节一致」。以下三项偏差只在比对**线上原始字节**时可见，仅靠 `http.Header` 层面的比对无法发现。

| 偏差 | 现象 | 处理方式 |
|---|---|---|
| **键名大小写被规范化** | Go `http.Header.Set` 经 `textproto.CanonicalMIMEHeaderKey` 改写键名：`X-Request-ID`→`X-Request-Id`、`X-IDE-Type`→`X-Ide-Type`、`X-B3-TraceId`→`X-B3-Traceid`、`x-requested-with`→`X-Requested-With` | 新增 `setHeaderExact`/`getHeaderExact` 直接读写 map 键，复刻客户端原始大小写 |
| **请求体键序被字典序化** | 经 `map[string]any` 中转再 `json.Marshal` 会按键名排序输出，`messages` 跑到 `model` 之前；客户端 `JSON.stringify` 按属性插入顺序输出，`model` 恒在首位 | 新增保序 JSON 层（`jsonorder.go`），解析/修改/序列化全程保持键序 |
| **`<` `>` `&` 被 HTML 转义** | `json.Marshal` 默认把 `<` 转成 `\u003c`；客户端正文含 `<user_query>` / `<content_policy>` 等标签，`JSON.stringify` 原样输出 | 自实现转义（仅处理 `"` `\` 与控制字符），与 `JSON.stringify` 口径一致 |
| **请求头物理顺序不同** | Go `net/http` 把 `Host` / `User-Agent` / `Content-Length` 单独前置，其余头部经 `http.Header`（map）按规范化键名字典序写出；客户端按**属性插入顺序**写出 | 新增 `wireorder.go`，在 conn 层按实测顺序重排模型请求头块（见下节） |
| **缺少 `Connection: keep-alive`** | 客户端由 Node http 模块在头部块末位补齐该头；Go transport 默认不写 | `backendHeaders` / `daemonHeaders` 显式设置（Go 会原样写出，且 HTTP/1.1 默认即长连接，语义不变）｜

**为什么必须保序保真**：这些偏差都无需解析语义、仅比对字节即可判定，是极强的机器特征。此外保序层用 `json.Number` 保留原始数字字面量，避免超出 2^53 的整数经 `float64` 中转被静默改写。

**关于 HTTP/2**：实测客户端走 Node 全局 `fetch`（undici），**默认 HTTP/1.1**（抓包中带 `Host` / `Connection: keep-alive`，这两个头在 HTTP/2 中非法）。故网关**不启用** HTTP/2 —— 启用反而会引入偏差，且 h2 的 HPACK 头压缩会让键名大小写与顺序信息消失。直连 https 时网关自建的拨号层亦不设置 ALPN，与客户端同样停在 HTTP/1.1。

### 请求头线上顺序对齐（v1.14.3 新增，v1.14.4 补 `Accept-Encoding` 槽位）

「头部集合与键名大小写一致」仍不等于「字节一致」：`net/http` 会把 `Host` / `User-Agent` / `Content-Length` 单独前置，其余头部经 `http.Header`（map）按**规范化键名字典序**写出，而客户端按**属性插入顺序**写出 —— 两者头部字节序列截然不同，同样无需解析语义即可判定。

`wireorder.go` 在 **conn 层**复刻该顺序（`installWireOrder`）：`net/http` 写头部的位置不可拦截，但其写出的字节必经 `net.Conn.Write`，故把 conn 包一层，在每个请求的头部块写出前按实测顺序重排。顺序基线取自三处实测：本机 5.7.6 客户端的线上字节抓包（`.client_ref/cap/intl_chat_capture.jsonl` / `intl_toolturn_capture.jsonl`，每条模型请求 39 个头）、一份按**线上字节顺序**记录的 5.5.2 桌面客户端抓包（38 个头），以及本机 5.5.3 国内站客户端链路的模型请求（`.client_ref/cap/cn_chat_capture.jsonl`，38 个头）。三者的应用层顺序完全一致；差异只在传输层末尾的 `Accept-Encoding`：国际站该头位于 `Content-Length` 与 `Host` 之间，国内站没有该头（尾部即 `Content-Length → Host → Connection`）。顺序表按**头名**匹配，缺席的头自然不写出，故两站共用一张表即可各自对齐。抓包含 Authorization 等凭据，属本地研究产物、不入仓库。成因可在 bundled CLI 源码中逐条定位：

```text
SDK 默认头 → 应用自建头表（会话/Agent/IDE/隐私标记）→ 处理器链（GzipRequestProcessor 末位，追加 Content-Encoding）
→ OTel + B3 传播头 → AuthenticationHttpInterceptor（Authorization/X-User-Id/X-Enterprise-Id/X-Department-Info/X-Tenant-Id/X-Domain）
→ X-Product / User-Agent → Node http 补齐 Content-Length / Accept-Encoding / Host / Connection
```

因 `Content-Encoding` 由处理器链（`priority=9999`）追加、传播头在其后注入，故 `Content-Encoding` 位于传播头**之前**；国际站最后四位为 `Content-Length` / `Accept-Encoding` / `Host` / `Connection`，国内站没有 `Accept-Encoding`，最后三位为 `Content-Length` / `Host` / `Connection`。

| 项 | 行为 |
|---|---|
| 生效范围 | 仅 `/v2/chat/completions`（唯一有逐字节实测顺序基线的一族；控制面 axios 族与守护进程 undici 族各自的头部对象由不同调用点构造，无实测顺序，不重排） |
| 生效路径 | 直连 https（`Transport.DialTLSContext`，返回的 conn 之上即明文头部）与明文 http（`DialContext`）；配置 `-proxy` 时 Go 自行 CONNECT + TLS，不存在明文层，**顺序复刻不生效**（头部集合与键名大小写仍保持对齐） |
| 安全前提 | 只重排「能确认是 HTTP/1.1 请求头」的字节；代理 CONNECT、TLS 密文、无法确认的字节流一律原样透传。正文只按 `Content-Length` 计数透传、绝不解析（正文本身可能含 `CRLFCRLF`），因此 keep-alive 复用连接上的后续请求也能被正确重排 |
| 失败即透传 | 头部块超过 64 KiB、请求行非法、头名非 RFC 9110 token、或规则未命中的头名，均按原顺序写出且字节不变 |

### 会话作用域对齐（v1.8.5 新增）

链路 ID 不是「每请求一套」，而是**两个作用域**。客户端源码（`chat_headers_full` 实测片段）写得很直白：

```js
ey[CONVERSATION_ID_HEADER]         = ew.id                     // 会话
ey[CONVERSATION_REQUEST_ID_HEADER] = ew.conversationRequestId  // 会话
ey[CONVERSATION_MESSAGE_ID_HEADER] = ew.messageId              // 每请求
ey[REQUEST_ID_HEADER]              = ew.messageId              // 每请求
```

| 头 | 作用域 | 实测不变量（9 条会话 / 19 次请求） |
|---|---|---|
| `X-Conversation-ID` | 会话 | 会话内恒定，带连字符 UUID **（v7）** |
| `X-Conversation-Request-ID` | 会话 | 会话内恒定，32 位 hex **（v7 紧凑形态，前 48 位与 `X-Conversation-ID` 同值）** |
| `X-Root-Request-ID` | 会话 | 会话内恒定，**等于** `X-Conversation-Request-ID` |
| `X-Trace-ID` | 会话 | 会话内恒定，**等于** `X-Conversation-Request-ID` |
| `X-B3-TraceId` | 会话 | 等于 `X-Trace-ID` |
| `X-Request-ID` | 每请求 | 每请求变化 |
| `X-Conversation-Message-ID` | 每请求 | 每请求变化，**等于** `X-Request-ID` |
| `traceparent` / `b3` / `X-B3-SpanId` / `X-B3-ParentSpanId` | 每请求 | span 部分每请求变化 |

网关此前把**四个会话级头也按请求新生成**，等于「同一会话的连续请求携带互不相同的会话链路 ID」—— 只要比对同一会话的两次请求即可判定，是稳定的机器特征。同时 `X-Conversation-Request-ID` 被错设为 `X-Request-ID`，单次请求内部即与客户端口径不符（前者应是会话级，后者是每请求级）。

**实现**：`prepareConversationContext` 在三个协议入口转换原请求之前解析[扩展会话键](#上游会话请求头v11420)，再由 fork 的 `resolveLinkIDs` / `newSessionScope` 统一生成自洽标识。会话级 ID 从解析后的会话键（仍兼容仅 `X-Conversation-Request-ID` 的输入）经 `SHA-256` 派生，不使用跨请求随机 ID 缓存；本次最终 link IDs 只在请求 Context 内缓存，供安全重试与跨账号回退复用。

| 方案 | 跨请求共享状态 | 并发 | TTL / 容量 | 重启后 |
|---|---|---|---|---|
| 随机生成 + map 缓存 | 需要 | 需加锁 | 需上限与过期 | 会话 ID 变化 |
| **哈希派生（采用）** | **无** | **无竞争** | **不需要** | **稳定** |

派生值取哈希 16 字节（32 位 hex），与客户端 `X-Conversation-Request-ID` 同形态，且不泄露会话键本身（客户端传入 32 位 hex，网关发出的同样是 32 位 hex）。位域布局沿客户端 2.156.0 的 UUID v7：模板（下游会话 ID）本身是 v7 时，派生值沿用其前 48 位毫秒时间戳并置版本位 `7`，使「会话 ID 与请求 ID 同一次生成」的时序关系成立；模板非 v7（老客户端）时退化为 v4 位域，不产出客户端不会生成的版本位与时间前缀。

**下游未携带会话标识时**（如第三方 OpenAI SDK 直连，只有 `messages` 没有会话头）：不臆造会话关联，会话级 ID 退回每请求新值 —— 与旧行为一致。把无会话语义的请求错误归并到同一条链路，反而会制造出「大量不相关请求共享同一 traceId」的异常模式。

**链路 ID 只有一个写入方**：这些头之间存在客户端保证的相等关系（`X-Trace-ID` == `X-Conversation-Request-ID` == `X-Root-Request-ID` == `X-B3-TraceId` == `traceparent` 的 trace 段 == `b3` 的 trace 段；span 段同理；`X-Request-ID` == `X-Conversation-Message-ID`）。

因此它们**不在透传白名单**里，而是由 `resolveLinkIDs` 统一决定：**下游给出同组任一项即采用该值，并据此补齐同组其余头**。

| 下游只提供 | 网关行为 |
|---|---|
| 仅 `traceparent` | 其 trace 段传播到 `X-Trace-ID` / `X-Conversation-Request-ID` / `X-Root-Request-ID` / `X-B3-TraceId`，span 段传播到 `b3` / `X-B3-SpanId` |
| 仅 `b3` | 同上，并取回 `X-B3-ParentSpanId` |
| 仅 `X-Request-ID` | 同步为 `X-Conversation-Message-ID` |
| 仅 `X-Conversation-Request-ID` | 原样采用，并补一个形态自洽的 `X-Conversation-ID` |
| 都不提供 | 全部新生成，组内自洽 |

逐头原样透传是错的：下游只给一部分时，网关会为其余头另生成值，产出**客户端不可能产生的组合**（如 `X-B3-SpanId` 与 `traceparent` 的 span 段不等）—— 这比单纯缺失更显眼。

> 补充：`X-Conversation-ID` 由客户端传入时会被原样采用，哈希派生只用于**下游缺失时**的合成，不会覆盖客户端真实会话键。

### 透传与合成的边界

下游客户端自带的**客户端族专有**身份头（`X-Agent-Intent`、`X-Agent-Purpose`、`X-IDE-*`、`X-Private-Data`、`x-codebuddy-request`、`X-B3-Sampled`、`x-requested-with`、`Accept`）优先透传，网关仅在缺失时回退合成值。

`User-Agent` 与 `x-stainless-*` **不接受透传**：只有官方客户端会发送这两组头，其取值即等于官方的产品与 SDK 版本；而第三方下游（Claude Code、Cursor 等）会带自己的 UA 与 SDK 版本，透传会让上游看到「WorkBuddy 的 IDE 头 + 别的客户端的 UA」这种官方客户端不可能产生的组合。故这两组一律按站点 Profile 合成。

鉴权类头（`Authorization`、`X-User-Id`、`X-Enterprise-Id`、`X-Tenant-Id`、`X-Domain`、`X-Product`、`X-Refresh-Token`）**一律由账号池生成，不接受下游覆盖**，以防串号或泄权。

### 回归保障

`main_test.go` 中的 `TestUpstreamFingerprintMatchesRealClient` 以真实抓包基线逐项校验（不多、不少、值一致、**键名大小写逐字一致**、链路 ID 形态与作用域自洽）；`TestSmokeEndToEndUpstreamHeaders` 驱动完整请求链路（含生产 transport）抓取实际发出请求头，覆盖单测无法触及的传输层差异；`TestCompressedUpstreamResponseIsDecoded` 覆盖响应侧压缩——假上游分别以 `br` / `gzip` / `deflate` / 不压缩四种方式返回同一段 SSE，断言下游收到明文事件与 `[DONE]`，并断言未支持编码（`zstd`）返回 `502 upstream_encoding_unsupported` 而非把压缩字节当明文；`TestCompressedUpstreamErrorResponseIsDecoded` 断言**错误**响应同样被解压（下游收到上游原文而非压缩字节）。

会话作用域与链路 ID 自洽性由四个端到端用例断言（均驱动真实 `handleChatCompletions` → `upstreamChat` → 生产 transport 链路）：

- `TestSessionScopedLinkIDsAreStableWithinConversation` —— 同会话连续两次请求：四个会话级头逐字恒定，`X-Request-ID` / `X-Conversation-Message-ID` / 两个 span ID 各不相同；
- `TestSessionScopedLinkIDsDifferAcrossConversations` —— 不同会话不共享会话级 ID；
- `TestNoConversationKeyFallsBackToPerRequestIDs` —— 无会话键时不臆造关联，退回每请求新值；
- `TestConversationRequestIDOnlyIsAdoptedVerbatim` / `TestPartialLinkHeadersAreCompletedCoherently` —— 下游只提供部分链路头时，按不变量补齐同组伙伴（仅 `traceparent` / 仅 `b3` / 仅 `X-Request-ID` / 都不提供 四种情形）。

字节级偏差由裸 TCP 监听（`captureUpstreamWire`，不经 `net/http` 解析器重新规范化）断言：

- `TestUpstreamWireHeaderCasingMatchesClient` —— 线上键名大小写逐字匹配客户端基线，且规范化形态绝不出现在线上；
- `TestUpstreamWireBodyMatchesClientEncoding` —— 线上请求体以 `model` 开头、`messages` 在其后、`<` `>` `&` 未转义、无尾随换行；
- `TestLoginWireHeadersMatchClient` —— 登录链路首跳（`auth/state`）的线上字节：控制面必需头逐字大小写齐全、`b3` 无父 span（末段为空）、`X-Request-ID` == `X-Trace-ID`，且 `traceparent` / `X-IDE-*` / `x-stainless-*` / 会话链路头一律不出现；
- `TestCatalogWireHeadersMatchDaemonFetch` —— 守护进程接口（实时模型目录）的线上字节：`X-Trace-Id` / `X-Request-ID` / `b3` / `user-agent` / `accept-encoding` 等键名逐字、`b3` 三段、`User-Agent: node`、无 `X-IDE-*` / `x-stainless-*` / `X-Product` / `traceparent` / `Content-Type`；
- `TestOrderedJSONContract` / `TestResponsesBodyKeyOrder` —— 保序层的键序、转义、数字精度与非法输入边界。

控制面头集合由另外三处断言把守：

- `TestLoginControlPlaneHeadersMatchClient` —— 登录三步（`auth/state` / `auth/token` / `login/account`）按各自**真实方法与 body** 断言控制面头集合、`X-No-*` 成组语义、模型专有头缺席，以及「`Content-Type` 只随 body 出现」（`auth/state` 的 POST 带、两个 GET 不带）；
- `TestRefreshRequestMatchesClientBody` —— 刷新链路的线上请求形状：`POST /v2/plugin/auth/token/refresh` 带 body `{}`（`Content-Length: 2`）与 `Content-Type: application/json`，控制面族头（`X-Refresh-Token` / `X-Auth-Refresh-Source: plugin` / `X-Domain` / `Authorization` / `X-User-Id` / `X-Product`）齐全，模型专有头一律缺席；
- `TestQuotaRefreshSeparatesQuotaAndPlanFailures` —— 额度摘要与套餐资源两个控制台接口走控制面集合（axios 族头在、`X-Client-Platform` 与模型专有头不在、`X-Request-ID` == `X-Trace-ID`），两个请求共用同一 traceId 且逐请求换 span；
- `TestCheckinAccountCNAndSkipIntl` —— 签到走控制面集合（国际站仍跳过）。

- 默认先运行 `go vet`、`go test`；不受调用者遗留的 `GOOS` / `GOARCH` 影响。各目标使用 `CGO_ENABLED=0`，x64 基线为 `GOAMD64=v1`、ARM64 基线为 `GOARM64=v8.0`。成功或失败后恢复原构建环境和工作目录。

- `-OutputDir` 必须是项目内的独立子目录；`-Clean` 仅清理已知构建文件，不递归删除目录、配置凭据或其他文件。构建日志写入 `logs/build-YYYY-MM-DD.jsonl`。
